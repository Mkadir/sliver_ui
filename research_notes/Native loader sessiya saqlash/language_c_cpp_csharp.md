## Why unsigned Go PEs trip `Trojan:Win32/Wacatac.B!ml` even when benign; would a MinGW C EXE of the same VirtualAlloc→XOR→VirtualProtect→CALL path avoid that stub class?

### Takeaway
`Wacatac.B!ml` is a Microsoft **static PE-ML** family (`!ml` = classifier, not a byte signature). Unsigned Go EXEs trip it because of **Go PE shape** (`gopclntab`, large `.text`, runtime symbols, statically linked, no CRT), and `-s -w` makes that worse. A CRT-free MinGW **C** stub of similar *behavior* should leave that **Go-shape stub class**; it would not leave the **unbacked RWX / ETW-Ti / decrypted Sliver** class.

### Cited Findings
- Formidable (Wails 3 + Go 1.25 GUI, May 2026): both NSIS installer and bare `Formidable.exe` flagged `Trojan:Win32/Wacatac.B!ml`. VirusTotal: installer 2/71 (Microsoft + Trapmine), bare EXE 1/71 (Trapmine). Four VT sandboxes (CAPA, CAPE, Jujubox, Zenbox) returned **0 dynamic detections**. VersionInfo, Win10/11 manifest, dropping `-s -w` (~30% size increase), reproducible `-buildid=`, NSIS polish, and an FP submission **did not** change the score. Author’s diagnosis: Defender ML weights **Go-binary PE shape** (large `.text`, `gopclntab`, `runtime.morestack_noctxt` / `runtime.gcWriteBarrier`, statically linked, no dynamic CRT) because Go malware volume since ~2020 (BlackCat/ALPHV, Sliver, stealers) trained “Go-shaped unsigned EXE” as a positive malware feature. Same product as Electron was never flagged. Remaining idea: **C/Win32 launcher + Go `-buildmode=c-shared` DLL**, because DLLs are scored differently from EXEs — [Formidable: Defender, Wacatac.B!ml, and the Go-binary problem](https://formidable.tools/posts/defender-wacatac-go-binary/).
- Praetorian (28 May 2026, “Adversarial Oracles”): Go hits are dominated by statistical ML (`Wacatac.B!ml`, `ML.Attribute.HighConfidence`) rather than fixed-byte YARA. Building goffloader with `-trimpath -ldflags "-s -w"` **increased** VirusTotal detections and did not remove package-name strings (Go keeps them for reflection). Garble **increased** detections further (CrowdStrike Falcon). ML over-indexes on **`gopclntab`**: a vanilla hello-world Go binary is ~2.5 MB with a ~100 KB `gopclntab` of mostly runtime symbols (`runtime.mallocgc`, `internal/poll.(*FD).Read`); that “small minimal binary with mostly runtime symbols” pattern looks like stripped malware. Diluting `gopclntab` with a large real-project “ghost profile” dropped Microsoft Wacatac from around **95% to around 20%** on otherwise-identical payloads. Stripping names entirely was the **worst** option: CrowdStrike and Symantec hit immediately. Fake MSVC Rich header / patched linker version / stripped `.symtab` made detections **worse** (“Don’t fight the toolchain”: 40 features still say Go, 1–2 now say MSVC, inconsistency is the signal). Microsoft **cloud** ML is “substantially more aggressive” than local `MpCmdRun.exe`; a 100% Wacatac VT hit can be clean locally. Wacatac retrains on a roughly daily cadence — [Praetorian: Adversarial Oracles](https://www.praetorian.com/blog/llm-edr-signature-reduction/).
- Microsoft documents client PE-type ML plus cloud metadata ML (PE attributes, hashes, ImpHash, signer, MotW, API calls, process injection) and an emulation engine that unpacks and examines memory at the end of emulation. Memory scanning is a **client** function with **no** cloud counterpart — [Advanced technologies of MDAV](https://learn.microsoft.com/en-us/defender-endpoint/adv-tech-of-mdav); [Cloud protection and sample submission](https://learn.microsoft.com/en-us/defender-endpoint/cloud-protection-microsoft-antivirus-sample-submission).
- Block at First Sight locks Internet-zone unknown EXEs ~10s (up to 60s) and can upload the sample; a new hash is a **first-seen** event, not an allow — [Configure block at first sight](https://learn.microsoft.com/en-us/defender-endpoint/configure-block-at-first-sight-microsoft-defender-antivirus).
- SmartScreen: unsigned files start at **zero** file-hash reputation; EV certs no longer confer instant reputation — [SmartScreen reputation for developers](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation).
- Current sliver-ui Windows stub is exactly the Go shape Praetorian/Formidable describe: `CGO_ENABLED=0` static PE, `-s -w`, unique `-buildid`, XOR-encrypted high-entropy `cfg.dat` embed, Go runtime still in IAT (`kernel32.dll` / `VirtualAlloc` / `CreateThread`) — [file:///home/cup/Documents/personal/sliv/backend/internal/loader/build.go](file:///home/cup/Documents/personal/sliv/backend/internal/loader/build.go); [file:///home/cup/Documents/personal/sliv/research_notes/Windows%20loader%20Defender%20sessiya%20muammosi/our_loader_techniques.md](file:///home/cup/Documents/personal/sliv/research_notes/Windows%20loader%20Defender%20sessiya%20muammosi/our_loader_techniques.md).
- ETW-Ti logs local `ALLOCVM` / `PROTECTVM` even without `CreateThread` — [adanto/EtwTiViewer](https://github.com/adanto/EtwTiViewer); [Elastic: Doubling Down on ETW call stacks](https://www.elastic.co/security-labs/doubling-down-etw-callstacks).
- gatari (2024): XOR of a blob passed **disk** scan; **RWX + direct CALL** was killed at runtime; VirusTotal upload burned the hash — [A Trip Down Memory Lane](https://gatari.dev/posts/memory-lane/).
- PEzor’s native path is a **C** `loader.c` plus C++ packer, with `-rx` (RX not RWX) documented as incompatible with SGN, and `-self` (same-thread CALL) requiring RX shellcode — [phra/PEzor](https://github.com/phra/PEzor).

### Inferences
- The current Go stub is in the **wrong PE-shape bucket** for Microsoft’s classifier even before XOR/RWX: Formidable’s *benign GUI* is the existence proof. Praetorian shows the product’s `-s -w` is the **wrong** Go mitigation (absence of debug data is itself a feature).
- A MinGW C EXE with no `gopclntab`, no Go runtime, no `.symtab` full of `runtime.*`, and a normal (or CRT-free) PE layout **should not** be scored as “Go malware shape.” That is the stub-class win. Formidable independently proposed a C launcher for this reason.
- The **same** VirtualAlloc RW → XOR decrypt → VirtualProtect RX/RWX → CALL sequence is still a **behavioral / ETW-Ti / emulator** class, independent of language. Switching to C does not make that sequence look like notepad. It only stops Defender from classifying the *file* as a Go implant/packer before it runs.
- Do not add a fake Rich header or patch the MinGW linker to look like MSVC. Praetorian’s “don’t fight the toolchain” result applies in reverse too: a C PE should look like a C PE.
- Hash uniqueness (`mintUniqueness` nonce / `n.bin` / `-buildid`) remains hash-IOC only. A C stub with a unique hash is still first-seen unsigned; BAFS/SmartScreen still apply.

### Gaps
- No public 2025–2026 A/B of “this exact 200-line MinGW C loader vs sliver-ui’s current Go stub” under the same MDAV cloud definition. Formidable and Praetorian are the closest primary evidence; they did not compile sliver-ui’s stub.
- Microsoft does not publish `Wacatac.B!ml` feature weights. “C avoids Wacatac” is an inference from Go-shape evidence, not a vendor statement.
- Trapmine (Formidable’s 1/71 on the bare EXE) is unsigned-generic ML; a tiny unsigned C loader can still trip generic ML. Magnitude is unknown.

## C vs C++: exceptions / RTTI / iostream IAT; `/MT` vs MinGW CRT (`msvcrt` vs none with `-nostdlib`); typical size of a 200-line loader

### Takeaway
Use **C**, not C++. A 200-line Win32 loader in CRT-free MinGW C is on the order of **1–10 KB** of stub (plus the embedded blob) with an IAT of `kernel32` (and `advapi32`/`user32` if persist/hide-console need them). Default C++ (`iostream`, exceptions, RTTI) pulls `libstdc++` / `libgcc` and balloons to **hundreds of KB** plus MinGW DLLs. MSVC `/MT` is a **Windows-only MSVC** product cost and is not available on the Linux UI host.

### Cited Findings
- CRT-free MinGW (Chris Wellons, 2023): `-nostartfiles` skips the CRT entry but still passes `-lmingw32 -lkernel32`; a program that only calls `ExitProcess` imports **only `KERNEL32.dll`**. `-nostdlib` passes **no** default libs; you must `-lkernel32` explicitly. Conventional entry names: `mainCRTStartup` (console) and `WinMainCRTStartup` (windows subsystem). Hide-console is `-mwindows`. Release-style line: `cc -O3 -fno-builtin -s -nostdlib -mwindows -fno-asynchronous-unwind-tables -o app.exe app.c -lkernel32`. `-nostartfiles` will silently pull `memset` from **`msvcrt.dll`** if the compiler inserts builtins; `-nostdlib` will not. Stack probes (`___chkstk_ms`) appear with large frames unless `-mno-stack-arg-probe` — [CRT-free in 2023](https://nullprogram.com/blog/2023/02/15).
- Ultra-small MinGW PE: `gcc -m32 -mconsole -nostdlib -nostartfiles -Os -s … -lkernel32 -luser32 -Wl,-e_mainCRTStartup` produced a **1056-byte** EXE importing only `kernel32.dll` and `user32.dll` (3 sections: `.text`, `.rdata`, `.idata`); later C-only work reached **964 bytes** — [KeyJ: Writing ultra-small Windows executables](https://keyj.emphy.de/win32-pe/) (comment thread, MinGW 4.9.2 / 2023–2026 follow-ups).
- Linking dynamically to `msvcrt.dll` (present since Windows 98/NT4) plus a ~40-line CRT stub yields ~**3 KB** PEs instead of >100 KB statically linked CRT — [modexp: Beacon Object Files vs Tiny EXE Files](https://web.archive.org/web/20250429092722/https://modexp.wordpress.com/2025/04/27/beacon-object-files-vs-tiny-executables/); [SolomonSklash: Smaller C payloads on Windows](https://www.solomonsklash.io/smaller-c-payloads-on-windows.html) (8×–12× size cut vs default CRT).
- mingw-w64 CRT choice: toolchain default is now **UCRT** (`api-ms-win-crt-*.dll`, inbox since Windows 10); `--with-default-msvcrt=msvcrt` keeps `msvcrt.dll`. `msvcrt.dll` is frozen ~1996-era and ships with the OS; UCRT is the modern default but is a **Vista+ redistributable / Win10+ inbox** dependency — [mingw-w64: ucrt-vs-msvcrt.txt](https://github.com/mingw-w64/mingw-w64/blob/master/mingw-w64-doc/howto-build/ucrt-vs-msvcrt.txt); [llvm-mingw README](https://github.com/mstorsjo/llvm-mingw/blob/master/README.md).
- C++ `iostream` on MinGW: a 10 KB `MessageBoxA` C++ file became **193 KB** with `std::string` and **756 KB** with `<iostream>`, even with `-s -Os -fno-exceptions -fno-rtti` — [C++ executable size using MinGW](https://exchangetuts.com/c-executable-size-using-mingw-1640916423798751). `<iostream>` is not in MSVCRT; MinGW links **`libstdc++-6.dll` + `libgcc_s_*.dll`** (or statically embeds them) because there is no Microsoft C++ ABI to share — [Why does iostream depend on MinGW DLLs?](https://stackoverflow.com/questions/51343564/why-does-iostream-depend-on-mingw-dlls). Another comparison: MinGW-GCC 4.4.1 iostream hello world **468 KB** vs `printf` **<10 KB** — [GCC Hello World 500 KB](https://ansaurus.com/question/1042773-gcc-c-hello-world-program-exe-is-500kb-big-when-compiled-on-windows-how-can-i-reduce-its-size).
- Exceptions/RTTI: `-fno-exceptions -fno-rtti` removes unwind/typeinfo; remaining C++ cost is still the standard library you actually use. On embedded GCC, those two flags dropped a C++ hello from ~5 KB to ~1 KB — [EM-IDE: GCC -fno-rtti -fno-exceptions](https://discuss.em-ide.com/d/583-gcc-c-fno-rtti-fno-exceptions). That does **not** remove `iostream` / locale.
- MSVC `/MT` statically links the Visual C++ CRT into the PE (typical “hello” tens–hundreds of KB, no `msvcr*.dll` dependency). `/MT` is an **MSVC cl.exe** flag; it is not a MinGW flag. Using it requires a Windows Visual Studio “Desktop development with C++” host — not this Linux UI host.
- PEzor’s in-process loader is **C** (`loader.c`: `VirtualAlloc`, PE refresh, custom GetProcAddress) compiled as part of a packer that also has C++ (`PEzor.cpp`) and optional `-format=dotnet` — [phra/PEzor loader.c](https://github.com/phra/PEzor/blob/master/loader.c); [PEzor README](https://github.com/phra/PEzor).
- This Linux host already has `x86_64-w64-mingw32-gcc` / `i686-w64-mingw32-gcc` (GCC 15-win32), `windows.h`, and both `libmsvcrt.a` and `libucrt*.a`. It does **not** have `x86_64-w64-mingw32-g++` (confirmed `command -v` → missing; dpkg has `gcc-mingw-w64-*-win32` but no `g++-mingw-w64-*`). Native Linux `g++` is not a Windows cross compiler.

### Inferences
- For a 200-line loader that is a C translation of `windowsSource()` (Win32 APIs, XOR loop, persist via `RegCreateKeyExW` / `CreateProcessW("schtasks")`, hide via subsystem), the right flags are MinGW **C**: `-nostdlib -fno-builtin -mno-stack-arg-probe -Os -s -mwindows` (when hide-console) `-lkernel32` plus `-luser32` / `-ladvapi32` / `-lshell32` only if those persist/hide paths stay. Expected stub size: low single-digit to low tens of KB **before** embedding the 16–30 MB Sliver PIC. The PIC dominates file size either way; the stub’s job is **PE shape and IAT**, not shrinking the implant.
- Prefer **CRT-free** (`-nostdlib`) over linking `msvcrt`/`ucrt` for IAT cleanliness: no `memset`/`__getmainargs`/`_initterm` imports, no CRT DLL. Cost: you must supply `memset`/`memcpy` if GCC inserts them, and you cannot use `printf`. That is acceptable for this stub.
- If CRT-free is too sharp for persist (`schtasks` via `CreateProcessW` is still kernel32/advapi32), `-nostartfiles` is the dummy-proof middle: may import `msvcrt.dll` for builtins. Still far cleaner than Go.
- C++ as “C with `//` comments” plus `-fno-exceptions -fno-rtti` is **not** better than C. The first `#include <iostream>` or a thrown exception reintroduces MinGW C++ ABI DLLs or a static libstdc++ blob — a new IAT/signature surface with zero product value. Do not add `g++-mingw-w64` just to write the stub in C++.
- `/MT` is irrelevant unless the product grows a Windows compile worker. Do not.

### Gaps
- No measurement in this pass of compiling sliver-ui’s exact 200-line C translation; sizes above are literature bounds for CRT-free C vs iostream C++.
- Debian/Kali mingw-w64 “win32” vs “posix” threading variants change which libgcc is linked; this host’s packages are `*-win32`. Exact default-spec file (`-specs`) was not dumped.
- Whether current Kali mingw defaults to UCRT or msvcrt for `x86_64-w64-mingw32-gcc` was not confirmed beyond both import libs being present. CRT-free avoids the question.

## C#: AMSI on .NET assemblies, `AmsiScanBuffer` for CLR, execute-assembly vs native EXE. Is C# a worse choice for a native Sliver PIC loader? When would C# be better?

### Takeaway
**Yes, C# is a worse choice** for a **native Sliver PIC** loader. A managed C# stub loads the CLR, and from .NET Framework 4.8 / modern CoreCLR, **in-memory `Assembly.Load(byte[])` is passed to `AmsiScanBuffer`**. Native C/MinGW does not. AMSI patching to get around that is itself a Defender family (`Win32/AMSI_Patch_T.B13`, `Behavior:Win32/AMSI_PATCH_T.B12`). C# is better only when the *payload* is a .NET assembly (Donut/execute-assembly tradecraft), not when the payload is Sliver PIC.

### Cited Findings
- Microsoft AMSI portal: AMSI is integrated into UAC, PowerShell, Windows Script Host, JavaScript/VBScript, Office VBA. It is an **opt-in host** API (file/memory/stream scan), not a kernel scanner of every native EXE — [AMSI portal](https://learn.microsoft.com/en-us/windows/win32/amsi/antimalware-scan-interface-portal).
- Microsoft Defender AMSI page (updated 2026): supported languages include PowerShell, JScript, VBScript, WSH, WMI, **“.NET Framework 4.8 or newer (scanning of all assemblies)”**, plus Microsoft 365 VBA/JS/XLM. AMSI is how MDAV inspects script and **in-memory PE** delivered through those hosts. Native Go/C EXEs are **not** listed as AMSI hosts — [AMSI on MDAV](https://learn.microsoft.com/en-us/defender-endpoint/amsi-on-mdav).
- CoreCLR source: `Amsi::IsBlockedByAmsiScan` loads `amsi.dll`, `AmsiInitialize(L"coreclr")`, then `AmsiScanBuffer` on the flat image bytes. Comment in-tree: **“This should only run on in memory loads, Assembly.Load(byte[]) for example. Loads from disk are already instrumented by Defender, so calling AmsiScanBuffer wouldn't do anything.”** — [dotnet/runtime `src/coreclr/vm/amsi.cpp`](https://github.com/dotnet/runtime/blob/main/src/coreclr/vm/amsi.cpp).
- .NET Framework 4.8 added AMSI for `Assembly.Load` (announced 2018; still the live behavior). Loading a known-bad assembly from a byte array raises `BadImageFormatException` HRESULT `0x800700E1` (“file contains a virus”) — [BorderGate: Assembly.Load & AMSI](https://www.bordergate.co.uk/assembly-load-amsi/); [dbrandau: AMSI Memory Patching](https://dbrandau.tech/amsi-memory-patching-via-native-api-calls/); Zscaler: `.NET in-memory assembly loads: instrumented in .NET 4.8+ in clr.dll and coreclr.dll`; AMSI content name `DotNet` / `coreclr` is the **full in-memory PE** — [Zscaler: Better know AMSI](https://www.zscaler.com/blogs/cybersecurity-best-practices/amsi).
- VeryLazyTech (operator methodology, not a FUD recipe): AMSI is active in PowerShell/WSH/Office/UAC **and** “.NET applications – Starting from .NET Framework 4.8, even in-memory loaded code is scanned”; “attackers often target older .NET versions like 4.7.2 or below, where this check doesn’t exist.” AMSI patch / `amsiInitFailed` / `AmsiScanBuffer` overwrite are listed as common *and signatured* bypasses — [VeryLazyTech: Antivirus bypass](https://www.verylazytech.com/windows/antivirus-av-bypass).
- Sliver’s own Donut default AMSI/WLDP bypass is already a **signature**: `Win32/AMSI_Patch_T.B13`, Elastic AMSI/WLDP patching, `Behavior:Win32/AMSI_PATCH_T.B12` — Fortbridge; [sliver#1759](https://github.com/BishopFox/sliver/issues/1759); [donut#165](https://github.com/TheWover/donut/issues/165). Prior sliver-ui research: native Go EXE is **not** an AMSI host; putting an AMSI patch in a native loader is an IOC, not a win — [file:///home/cup/Documents/personal/sliv/reports/Windows%20loader%20Defender%20sessiya%20muammosi.md](file:///home/cup/Documents/personal/sliv/reports/Windows%20loader%20Defender%20sessiya%20muammosi.md).
- Microsoft hunting (2022, still the primary vendor Sliver write-up): default Sliver `execute-assembly` is `VirtualAllocEx` → `WriteProcessMemory` → `VirtualProtectEx` → `CreateRemoteThread` into a sacrificial process (often `notepad.exe`); MDE alert “A process was injected with potentially malicious code” — [Looking for the Sliver lining](https://www.microsoft.com/en-us/security/blog/2022/08/24/looking-for-the-sliver-lining-hunting-for-emerging-command-and-control-frameworks/).
- NativeAOT: publishes a **native** PE with a stripped CoreCLR statically linked; **no JIT**, **no `Assembly.LoadFile`**, typical console size **~4–15 MB** even with size flags (not KB). Windows NativeAOT publish officially wants VS 2022 “Desktop development with C++”. .NET Conf 2023: **“you cannot publish cross-platform”** NativeAOT (must be on the same OS you publish for, or use Docker/WSL). NativeAOT still embeds a runtime (GC, thread pool) — [Native AOT deployment overview](https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/); [Native AOT vs R2R vs JIT](https://startdebugging.net/2026/05/native-aot-vs-readytorun-vs-jit-in-dotnet-11/).
- This host has `/usr/bin/dotnet` **SDK 6.0.400** only, no `csc`/`mcs`. No Windows NativeAOT toolchain. Framework-dependent `win-x64` IL publish is possible from Linux; it still needs a CLR on the target and is still an AMSI host if it `Assembly.Load`s.
- PEzor offers `-format=dotnet` / `dotnet-pinvoke` / `dotnet-createsection` as **separate** output formats from the native C loader — [phra/PEzor](https://github.com/phra/PEzor). That is the industry split: native stub vs .NET stub, not “C# is a drop-in for C.”

### Inferences
- A C# EXE whose `Main` P/Invokes `VirtualAlloc` / `VirtualProtect` and `Marshal.Copy`s PIC still:
  1. Loads `clr.dll` / `coreclr.dll` (Sysmon 7 / image-load telemetry; “CLR in a non-.NET process” if injected).
  2. Has a PE shape of a .NET assembly (COM descriptor, `mscoree.dll` IAT, CLR header) — a **different** ML bucket from Go, not necessarily a quieter one for unsigned first-seen.
  3. If it then `Assembly.Load`s anything (or if operators later paste execute-assembly patterns into the stub), **AMSI sees the full PE bytes**.
- Patching `AmsiScanBuffer` from that stub recreates the exact IOC sliver-ui already decided not to ship (Donut Bypass=3). Do not.
- NativeAOT would dodge `Assembly.Load` AMSI for the *stub itself* (there is no managed load), but: (a) 4–15 MB stub vs 1–10 KB C; (b) cannot cross-compile from this Linux host without a Windows/Docker native toolchain; (c) still a large unsigned PE with a distinctive NativeAOT runtime; (d) product SDK is 6.0, not a current NativeAOT-friendly 8/9/11 SDK. NativeAOT does not beat C for this job.
- **When C# is better (narrow):**
  - The operator’s *payload* is a .NET tool (Seatbelt, Rubeus, custom C#) and the delivery path is **Donut PIC of that assembly** consumed by a **native C** stub — C# is the inner artifact, C is still the loader.
  - AppDomain / `execute-assembly` from an *already-running* Sliver session (post-ex), which is a different product surface (session Advanced), not `POST /api/loaders/build`.
  - A signed-looking “normal” .NET desktop app as a **parent** that sideloads a native DLL (Formidable’s launcher idea, inverted). That is an external packaging story, not the in-tree stub, and still does not hide the inner Sliver.
- Targeting .NET 4.7.2 to skip AMSI (VeryLazyTech) is a decaying lab trick: Win10/11 boxes have 4.8+, and “old runtime + unsigned EXE + VirtualAlloc” is its own signal. Do not productize it.

### Gaps
- No 2026 MDAV rate for “hello C# P/Invoke VirtualAlloc EXE” vs “hello MinGW C VirtualAlloc EXE” under identical cloud protection. Direction of AMSI cost is documented; magnitude of PE-ML difference is not.
- NativeAOT-from-Linux via Docker was not tested on this host.
- Whether .NET 8+ on Windows still always AMSI-scans `Assembly.Load(byte[])` is confirmed by current `dotnet/runtime` `amsi.cpp`; Framework 4.8 behavior is independently confirmed. CoreCLR hosting tricks (IBM X-Force `Load_2`, custom `ProvideAssembly`) exist to *avoid* AMSI; they are extra IOCs and out of product scope.

## Zig `zig cc` / Nim / Rust `no_std`: toolchain on a Linux UI host, size, IAT cleanliness vs C

### Takeaway
None of Zig-the-language, Nim, or Rust `no_std` **beat C** for this stub. Zig **as `zig cc`** is the only adjacent win: one ~40 MB toolchain that cross-compiles the **same C** to amd64/386/**arm64** Windows without llvm-mingw. This host has **neither Zig nor Nim**; `rustc` is present but only `x86_64-unknown-linux-gnu` is installed.

### Cited Findings
- Zig first-class cross-compile: `zig build-exe hello.zig -target x86_64-windows` emits a PE32+ Windows EXE from any host; Zig **ships libc** (including `x86_64-windows-gnu`, `x86-windows-gnu`) — [Zig overview: cross-compiling](https://ziglang.org/learn/overview/). `zig cc -target x86_64-windows-gnu -o hello.exe hello.c` is a documented drop-in for gcc/clang; Andrew Kelley’s original post compiles C to Windows from Linux and runs it under Wine — [zig cc: drop-in replacement](https://andrewkelley.me/post/zig-cc-powerful-drop-in-replacement-gcc-clang.html) (also mirrored in [ziglang.com.br cross-compile guide](https://ziglang.com.br/artigos/zig-cross-compilation-guia/) quoting `zig cc -target x86_64-windows-gnu`). CMake mapping includes `Windows`+`aarch64` → `aarch64-windows-gnu` PE — [zig.toolchain.cmake troubleshooting](https://deepwiki.com/tayne3/zig.toolchain.cmake/5.3-troubleshooting).

This host: `nim not found`.
- Rust: `rustc` 1.100 nightly is installed; `rustup` exists; **installed target is only** `x86_64-unknown-linux-gnu`. Target list includes `x86_64-pc-windows-gnu`, `i686-pc-windows-gnu`, `aarch64-pc-windows-msvc`, `aarch64-pc-windows-gnullvm` — none installed. `windows-gnu` still needs MinGW; `windows-msvc` needs MSVC/lld-link and is the Windows-host path. `no_std` Windows EXEs are possible but require a custom `#[panic_handler]`, no alloc unless you add one, and a linker script / `windows_sys` crates; they do not beat CRT-free C on IAT (both can import only `kernel32`) and add a second toolchain + nightly features.
- llvm-mingw (not installed): one Clang/LLD package targeting **i686, x86_64, armv7, aarch64** Windows from Linux; GCC mingw **does not support Windows on ARM**. CRT choice UCRT (default) vs msvcrt. Prebuilt `llvm-mingw-*-ubuntu-*.tar.xz` unpacks on Linux — [mstorsjo/llvm-mingw README](https://github.com/mstorsjo/llvm-mingw/blob/master/README.md); [ROllerozxa: Cross-compiling with llvm-mingw](https://voxelmanip.se/2024/12/10/cross-compiling-for-windows-using-llvm-mingw/). GNU `aarch64-w64-mingw32` is still a WIP project — [mingw-woarm64-build](https://github.com/Windows-on-ARM-Experiments/mingw-woarm64-build). ### Inferences
- **Zig-the-language** does not beat C: you would rewrite the stub, ship Zig on the UI host, and (unless you write freestanding Zig talking only to `kernel32`) pull Zig std into the PE. **Zig-as-`zig cc`** *does* beat *gcc-mingw* on **arm64 coverage and install surface** (one binary vs gcc-mingw + llvm-mingw). Product-wise: keep the stub in C; optionally compile it with `zig cc` if/when arm64 matters.
- **Nim** is a popular red-team *source* language because it cross-compiles through MinGW and has `winim`. After size flags you still have a **~50 KB** GC runtime PE, a Nim-shaped string table, and a public-tool signature surface (OffensiveNim, Nimcrypt, NimPackt). That is the opposite of “maximally nativize.” It requires adding Nim **and** still using mingw. Do not.
- **Rust `no_std`** can match C’s IAT in skilled hands and is not an AMSI host. It does not match C on: host bootstrap (`rustup target add` × 3, mingw or llvm, panic/alloc glue), compile latency, or operator-visible source simplicity for a 200-line loader. Not worth it unless the product already standardized on Rust.
- Public Nim/Zig/Rust loaders that “beat Defender in a blog” almost always add **syscalls, unhooking, AMSI/ETW patches** — techniques sliver-ui has already ranked as out of tree (ScareCrow/Freeze class). Language is not what made those posts work, and those posts rot.

### Gaps
- Zig 0.13+ Windows `ReleaseSmall` size for a 200-line `kernel32`-only loader was not compiled here (Zig absent).
- Rust `windows-gnu` `no_std` hello size was not compiled (target absent).
- Whether Kali’s `zig` package (when installed) ships the same mingw headers as system mingw-w64 was not checked.

## What detections remain identical regardless of stub language because the implant is still Sliver Go in the same process?

### Takeaway
After a successful jump, the process is a **16–30 MB Go Sliver implant** plus unbacked executable memory plus default C2. Memory YARA (`sliverpb`, protobuf RPC names, `Go buildinf`), Elastic `Multi_Trojan_Sliver`, Fortbridge Defender strings, unbacked-RWX / “network library loaded from unbacked memory,” ETW-Ti on the alloc/protect that mapped the PIC, beacon C2 (`.woff`/`.js`/JARM), and `Behavior:Win32/CommandAndControl.*!ml` **do not care** whether the stub was Go, C, C++, C#, Nim, Zig, or Rust. Changing the stub language is a **pre-jump PE-shape** control.

### Cited Findings
- Immersive Labs: average Windows Sliver ~**16 MB** unpacked in memory regardless of packing; Fortbridge observed up to **~30 MB**. Packing does not keep the Go image off the heap once the PIC runs — [Immersive: Detecting and decrypting Sliver C2](https://www.immersivelabs.com/resources/c7-blog/detecting-and-decrypting-sliver-c2-a-threat-hunters-guide); [Fortbridge: Reforging Sliver](https://fortbridge.co.uk/research/reforging-sliver-how-simple-code-edits-can-outmaneuver-edr/).
- Elastic `Multi_Trojan_Sliver` (`scan_context = "file, memory"`) keys on `ScreenshotReq`, `HTTPSessionInit`, `RequestResend`, `GetPrivInfo`, `github.com/bishopfox/sliver/protobuf` — [Multi_Trojan_Sliver.yar](https://github.com/elastic/protections-artifacts/blob/main/yara/rules/Multi_Trojan_Sliver.yar). Immersive memory rule matches `sliverpb` alone — [sliver.yar](https://github.com/Immersive-Labs-Sec/SliverC2-Forensics/blob/main/Rules/sliver.yar).
- Fortbridge extracted Defender-oriented YARA on `DllUnregisterServer`, `GetJitter`, `VoidFunc`, `AddTunnel`, `GetIsIOC`, `Go buildinf:`. Encrypt-in-loader was **ineffective** against Elastic+Defender; the path that worked was protobuf/export/string cleaning **plus LoadLibrary from disk** (not VirtualAlloc unbacked shellcode). Built-in commands still tripped Elastic behavior. Module stomping was abandoned at 30 MB Go. Elastic also alerted **“Network Library Loaded from Unbacked Memory”** when Go `LazyDLL`/`LoadLibraryExW` ran from private executable memory — [Fortbridge: Reforging Sliver](https://fortbridge.co.uk/research/reforging-sliver-how-simple-code-edits-can-outmaneuver-edr/).
- BishopFox maintainers: garble often fails to obfuscate protobuf methods; “several Defender AV signatures detecting these strings” — [sliver#1760](https://github.com/BishopFox/sliver/issues/1760). Project policy: AV evasion is out of scope — [Sliver Docs: Anti-virus Evasion](https://sliver.sh/docs?name=Anti-virus+Evasion).
- Stock Sliver has **no sleep mask**; idle implant stays plaintext in memory (Fortbridge; moloch: Go runtime makes this hard; PR #1805 not merged) — [sliver#1171](https://github.com/BishopFox/sliver/discussions/1171); [PR #1805](https://github.com/BishopFox/sliver/pull/1805).
- `interactive` / Open Session is a **goroutine in the same PID**, not a new PE — [Sliver tutorials: Beacons vs Sessions](https://sliver.sh/tutorials/?name=2+-+Beacons+vs+Sessions). UI `OpenSessionFromBeacon` does not generate a new implant.
- Microsoft: Sliver post-ex injection chain `VirtualAllocEx` → `WriteProcessMemory` → `VirtualProtectEx` → `CreateRemoteThread` — [Sliver lining](https://www.microsoft.com/en-us/security/blog/2022/08/24/looking-for-the-sliver-lining-hunting-for-emerging-command-and-control-frameworks/).
- Default HTTP C2 still looks like Sliver to public detectors (`.woff` stager, `.html` key exchange, `.js` long-poll, `.php` session, `.png` close) — [Sliver HTTPS C2](https://sliver.sh/docs/?name=HTTPS+C2); Immersive Labs (same as above).
- MDAV memory scanner has **no cloud counterpart**; it scans the running process — [adv-tech-of-mdav](https://learn.microsoft.com/en-us/defender-endpoint/adv-tech-of-mdav). Client behavioral blocking can kill a process **after** start (`Behavior:Win32/CommandAndControl.*!ml`, event 1015) — [Client behavioral blocking](https://learn.microsoft.com/en-us/defender-endpoint/client-behavioral-blocking).
- ETW-Ti `ALLOCVM`/`PROTECTVM` fire on the stub’s mapping of PIC **before** language-specific runtime details; Elastic `unbacked_rwx` / `execute_shellcode` are call-stack rules, not “was this compiled with Go?” — [Elastic: Doubling Down](https://www.elastic.co/security-labs/doubling-down-etw-callstacks).
- Prior product report: unique SHA-256 is hash-IOC only; XOR/RWX/no-CreateThread/hide-console/persist do not protect the live implant — [file:///home/cup/Documents/personal/sliv/reports/Windows%20loader%20Defender%20sessiya%20muammosi.md](file:///home/cup/Documents/personal/sliv/reports/Windows%20loader%20Defender%20sessiya%20muammosi.md).

### Inferences
- Ranked leftover classes after a C stub jump (same as after a Go stub jump):
  1. **Memory YARA / protobuf / `sliverpb` / `Go buildinf`** — implant source problem (garble, fork, string-clean). Not a stub-language problem.
  2. **Unbacked executable + Go `LoadLibrary` from private RX** — Fortbridge’s Elastic hit. A C stub that CALLs Donut PIC still leaves the implant’s *own* unbacked image. Disk `LoadLibrary` of a `format=shared` DLL was Fortbridge’s working *loader* shape; that is a **form-factor** change (DLL on disk), not a C-vs-Go compile flag.
  3. **ETW-Ti on the stub’s VirtualAlloc/VirtualProtect** — language-independent. RX instead of RWX may reduce one heuristic (PEzor `-rx`); Donut/SGN self-mod may still need RWX (already documented in sliver-ui).
  4. **C2 / JARM / default paths / long-poll** — HTTP C2 profile work, already a different UI page.
  5. **Behavior:Win32/CommandAndControl** on a live interactive session — same PID, same implant.
  6. **Post-ex injection** (`migrate`, `execute-assembly`, `sideload`) — Microsoft’s documented chain; unrelated to stub language.
- Therefore: moving Windows `loader.Build` from Go to MinGW C is justified as **nativizing the first-drop PE** (Wacatac / Go-shape / `gopclntab` / `-s -w`). It is **not** a session-preservation feature. Copy and UI must not say otherwise.

### Gaps
- No 2026 MDAV Protection History name captured for “MinGW C XOR+RWX+CALL of Sliver PIC” vs “Go stub of same PIC” on the same VM. Expected split: stub-class names (`Wacatac`, `ML.Attribute.*`) may drop; implant-class names (`Sliver`, `Behavior:Win32/CommandAndControl`, memory YARA) should not.
- Exact current Defender YARA for `Go buildinf` / protobuf is not public; Fortbridge extract lags the cloud.
