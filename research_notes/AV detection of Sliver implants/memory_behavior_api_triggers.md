# Memory and behavioral API triggers for a running Sliver Windows implant

Lab / detection-research notes. Scope is **post-execution**: the implant is already running (session or beacon callback). This is **not** on-disk PE ML / SmartScreen / BAFS. No malware PoCs.

Three independent sensor classes must be kept distinct throughout:

| Sensor class | What it actually sees | Typical trigger on a live Sliver implant |
| --- | --- | --- |
| **IAT / PE import table** | Win32 names in the on-disk (or mapped) PE import directory (`VirtualAlloc`, `LoadLibraryExW`, `WinHttpOpen`, …). Cloud metadata ML also consumes “API calls” as a **file feature**. | On-disk EXE/DLL only. PIC / Donut shellcode has **no IAT of its own**; the host process IAT is irrelevant. |
| **ETW of the syscall** | Kernel `Microsoft-Windows-Threat-Intelligence` events from `ntoskrnl` (`EtwTiLogAllocExecVm`, `EtwTiLogProtectExecVm`, …). Fires on `NtAllocateVirtualMemory` / `NtProtectVirtualMemory` even if the Win32 name is not in any IAT and even if the caller used a direct syscall. | ALLOCVM / PROTECTVM / MAPVIEW / WRITEVM on executable private memory. Elastic 8.11+ enriches these with call-stack behaviors (`unbacked_rwx`, `direct_syscall`, `sensitive_api`). |
| **Memory scan after those APIs ran** | Periodic / event-triggered scan of process VA for YARA / family strings. Independent of how the bytes got there. Microsoft documents a **client-only** memory-scanning engine (no cloud counterpart). | Protobuf method names (`ScreenshotReq`, `HTTPSessionInit`, …), `github.com/bishopfox/sliver`, ` Go buildinf:`, `GetJitter` / `VoidFunc` / `AddTunnel`. Fortbridge: a `bishopfox` hit appeared **only while the implant was running**. |

## Detection layers that fire after the implant is executing

### Takeaway
Once a Windows Sliver implant is in memory and has callback, documented kills are (1) **memory YARA** on plaintext Go/protobuf, (2) **unbacked executable memory** (`MEM_PRIVATE` RX/RWX from `VirtualAlloc`/`NtAllocateVirtualMemory`, not `MEM_IMAGE`), (3) **ETW-Ti ALLOCVM/PROTECTVM** on those regions, (4) **network-module load / `connect` from an Unbacked call stack** (`LoadLibraryExW` of `wininet.dll`/`winhttp.dll`/`ws2_32.dll`, or Winsock `connect`), (5) **Defender behavior ML** named `Behavior:Win32/CommandAndControl.*!ml` plus injection alerts on post-ex, and (6) **AMSI only** if a supported host (PowerShell, WSH, CLR 4.8+) is later invoked. HTTP URI fingerprints (`.woff`/`.php`/`.js`) are a **network** detector, not an API detector.

### Cited Findings
- Microsoft Defender’s **post-execution** client engines are behavior monitoring, AMSI, emulation, and memory scanning; the memory-scanning engine has **no cloud counterpart**. Client behavior monitoring “observes process behaviors, including behavior sequence at runtime.” Cloud “behavior-based ML” is triggered by “suspicious behavior sequences and advanced attack techniques” spanning exploits through exfiltration. A separate **network engine** “inspects network activities to identify and stop malicious activities.” — [Advanced Technologies at the Core of Microsoft Defender Antivirus](https://learn.microsoft.com/en-us/defender-endpoint/adv-tech-of-mdav) (Microsoft Learn)
- Memory protection table in the same article: client = Behavior Monitoring + AMSI + Emulation + Memory scanning; cloud = Behavior-based ML + AMSI-paired ML + Detonation ML; memory scanning = **N/A in cloud**. FAQ points to reflective-DLL hunting as the canonical memory-attack example. — [adv-tech-of-mdav, “Memory protection and memory scanning”](https://learn.microsoft.com/en-us/defender-endpoint/adv-tech-of-mdav); [Detecting reflective DLL loading with Windows Defender ATP (2017)](https://www.microsoft.com/en-us/security/blog/2017/11/13/detecting-reflective-dll-loading-with-windows-defender-atp/) (Microsoft Security Blog)
- Behavior monitoring “observes process, file, and service activity in real time.” Examples given: unusual file changes, ASEP registry modification. It is **required** for antimalware file-hash indicators **and** for Network protection (IP/URL indicators). Detections use the **Behavior** malware naming type. — [Behavior monitoring in Microsoft Defender Antivirus](https://learn.microsoft.com/en-us/defender-endpoint/behavior-monitor) (Microsoft Learn)
- `VirtualAlloc` commits pages with an explicit protection (`PAGE_EXECUTE_READWRITE` = `0x40`, `PAGE_EXECUTE_READ` = `0x20`, `PAGE_READWRITE` = `0x04`). Those constants apply to a **whole page**. — [VirtualAlloc](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-virtualalloc); [Memory Protection Constants](https://learn.microsoft.com/en-us/windows/win32/memory/memory-protection-constants) (Microsoft Learn / Win32)
- `MEMORY_BASIC_INFORMATION.Type`: `MEM_IMAGE` (`0x1000000`) = “mapped into the view of an **image section**”; `MEM_MAPPED` (`0x40000`) = mapped section; `MEM_PRIVATE` (`0x20000`) = “private (that is, not shared by other processes).” `AllocationBase` is “a range of pages allocated by the VirtualAlloc function.” — [MEMORY_BASIC_INFORMATION](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-memory_basic_information) (Microsoft Learn)
- Kernel ETW-Ti (`Microsoft-Windows-Threat-Intelligence`) is Microsoft’s post-PatchGuard telemetry for a “handful of highly security-relevant syscalls.” Elastic lists the Win32 names they propagate from it: `VirtualAlloc`, `VirtualProtect`, `MapViewOfFile`, `VirtualAllocEx`, `VirtualProtectEx`, `MapViewOfFile2`, `QueueUserAPC`, `SetThreadContext`, `WriteProcessMemory` (plus later `ReadProcessMemory` of lsass). Call-stack **behaviors** include `unbacked_rwx`, `direct_syscall`, `native_api`, `sensitive_api`, `shellcode`, `allocate_shellcode`, `execute_shellcode`, `execute_fluctuation`, `write_fluctuation`, `hollow_unbacked`, `hook_unbacked`. — [Doubling Down: Detecting In-Memory Threats with Kernel ETW Call Stacks](https://www.elastic.co/security-labs/doubling-down-etw-callstacks) (Elastic Security Labs, 2024-01-09)
- ETW-Ti logging is **inside the kernel**: `EtwTiLogAllocExecVm` from `MiAllocateVirtualMemory`; `EtwTiLogProtectExecVm` from `NtProtectVirtualMemory`. User-mode unhooking does not remove these. Subscribers must be PPL-Antimalware. — [Detecting Process Injection with ETW](https://blog.redbluepurpl.com/windows-security-research/kernel-tracing-injection-detection) (independent research, 2022); Elastic’s own description of the same provider — [Doubling Down](https://www.elastic.co/security-labs/doubling-down-etw-callstacks)
- Elastic YARA `Multi.Trojan.Sliver` is explicitly `scan_context = "file, memory"`. One rule keys on protobuf-generated names (`InvokeSpawnDllReq`, `HTTPSessionInit`, `ScreenshotReq`, `RegistryReadReq`, `NetstatReq`) plus `B/Z-github.com/bishopfox/sliver/protobuf/sliverpbb`. Another keys on Go method suffixes (`.RequestResend`, `.GetPrivInfo`, …). A third keys on x86/x64 **session-start / register** instruction sequences. — [Multi_Trojan_Sliver.yar](https://github.com/elastic/protections-artifacts/blob/main/yara/rules/Multi_Trojan_Sliver.yar) (Elastic protections-artifacts)
- Fortbridge (Apr 2025, vendor-blog / red-team writeup vs Elastic + Defender): staged / self-inject / pack of stock Sliver “proved ineffective.” After protobuf-string cleanup, **Elastic still alerted** `Network Library Loaded from Unbacked Memory` because HTTP beacon init uses Go `LazyDLL` → `LoadLibraryExW` from the shellcode region. Writing a DLL to disk and `LoadLibrary` of it **succeeded** against that Elastic rule. Remaining Defender hits were ASCII strings (`GetJitter`, `VoidFunc`, `AddTunnel`, `GetIsIOC`, ` Go buildinf:`, `DllRegisterServer` / `DllInstall`) plus a **runtime-only** YARA on `bishopfox`. Sliver “lack of a sleep mask” is called out as leaving the implant visible in idle memory. — [Reforging Sliver](https://fortbridge.co.uk/research/reforging-sliver-how-simple-code-edits-can-outmaneuver-edr/) (Fortbridge, 2025-04-01)
- Microsoft (2022 Security Blog, **not** Learn): default Sliver **post-ex** `migrate` / `sideload` / `spawndll` / `execute-assembly` / `msf-inject` / `getsystem` uses `VirtualAllocEx` → `WriteProcessMemory` → `VirtualProtectEx` → `CreateRemoteThread`. MDE example alert: **“A process was injected with potentially malicious code.”** Microsoft also extracted **in-memory** implant config because Sliver must decrypt it to check in. — [Looking for the ‘Sliver’ lining](https://www.microsoft.com/en-us/security/blog/2022/08/24/looking-for-the-sliver-lining-hunting-for-emerging-command-and-control-frameworks/) (Microsoft Security Blog, 2022-08-24)
- Elastic 8.8 used **Sliver `execute-assembly`** as the worked example of `clr.dll` loaded from unbacked RWX (`call_stack_summary : "*mscoreei.dll|Unbacked*"`). — [Upping the Ante: Detecting In-Memory Threats with Kernel Call Stacks](https://www.elastic.co/security-labs/upping-the-ante-detecting-in-memory-threats-with-kernel-call-stacks) (Elastic Security Labs, 2023-05-31)
- gatari.dev (independent, 2024-03): a loader that did `VirtualAlloc(PAGE_EXECUTE_READWRITE)` → `RtlMoveMemory` → **direct CALL of the pointer (no `CreateThread`)** was still flagged by Defender **after** static signatures were gone, because that call sequence is “very well known.” Switching to RW alloc + `VirtualProtectEx` RX + `QueueUserAPC` changed the **execution** API and got a callback in that author’s Defender-enabled folder (later cloud-hashed). — [A Trip Down Memory Lane](https://gatari.dev/posts/memory-lane/) (gatari.dev)

### Inferences
- A **disk-backed** Sliver EXE/DLL (`MEM_IMAGE`) and a **PIC/Donut** Sliver (`MEM_PRIVATE` executable) present two different post-exec surfaces. The former still has protobuf in image memory (memory YARA) and C2 network behavior. The latter **adds** unbacked-call-stack rules on every subsequent sensitive API (`LoadLibraryExW`, `connect`, `VirtualProtect`).
- Skipping `CreateThread` does **not** skip ALLOCVM/PROTECTVM: those ETW-Ti events are on the memory manager, not on the thread API.
- Microsoft’s 2022 hunt is primarily about **post-ex CRT inject**, not about the stock implant’s own HTTP poll loop. Elastic’s 8.8/8.11 rules **are** about the implant (or its loader) running from unbacked memory and then touching network / CLR APIs.

### Gaps
- Microsoft does not publish the live `Behavior:Win32/CommandAndControl.*` feature list or which ETW-Ti events the MDAV behavior engine consumes. That mapping is inferred from Learn engine descriptions + MDE alert text, not from a public rule body.
- No public Microsoft document states “Sliver HTTP beacon → `Behavior:Win32/CommandAndControl`.” The `CommandAndControl` **prefix** is the MITRE-tactic bucket, not a Sliver family name.

## Microsoft Defender: `Behavior:Win32/CommandAndControl.*`, events 1116 / 1117 / 1015, client behavioral blocking

### Takeaway
Microsoft Learn documents `Behavior:Win32/CommandAndControl.*!ml` as the **MITRE-tactic name** for behavior-based detections, **not** a published list of APIs. Client behavioral blocking sends “suspicious behaviors and their **process trees**” to cloud ML and can kill a process **after it has started**. Event **1015** is the dedicated “suspicious behavior” event; **1116/1117** are the general malware detected / action-taken events and can come from file, AMSI, NIS, or real-time — they do **not** by themselves prove a behavioral detection. Cited telemetry is process/file/service sequences, process trees, and (separately) a network engine + NIS “incoming/outgoing traffic” origin — **not** a public `WinHttpSendRequest` signature.

### Cited Findings
- Behavior-based detections are named from the MITRE ATT&CK matrix. The Command and Control row is exactly `Behavior:Win32/CommandAndControl.*!ml`. Other live-implant-relevant buckets: `Execution`, `DefenseEvasion`, `Collection`, `Exfiltration`, `Generic`. — [Client behavioral blocking](https://learn.microsoft.com/en-us/defender-endpoint/client-behavioral-blocking) (Microsoft Learn, page date 2025-04-25)
- “Microsoft Defender Antivirus can detect suspicious behavior, malicious code, fileless and in-memory attacks, and more on a device. When suspicious behaviors are detected, Microsoft Defender Antivirus monitors and sends those suspicious behaviors **and their process trees** to the cloud protection service. Machine learning … classifies each artifact. … as soon as an artifact is found to be malicious, it’s blocked on the device.” Client behavioral blocking “can help stop an attack that has begun executing.” Enabled by default when using Defender for Endpoint. — [Client behavioral blocking](https://learn.microsoft.com/en-us/defender-endpoint/client-behavioral-blocking) (Microsoft Learn)
- Behavioral blocking and containment components: ASR rules, client behavioral blocking, feedback-loop blocking, EDR in block mode. Documented techniques it has blocked include **cross-process injection**, **process hollowing**, **“Contacting Command and Control (C&C) to download payloads”**, LSASS dump, AV tampering, coin mining, boot-record modification. — [Behavioral blocking and containment](https://learn.microsoft.com/en-us/defender-endpoint/behavioral-blocking-containment) (Microsoft Learn, updated 2026-05-06)
- Microsoft malware naming: besides Backdoor/Trojan/VirTool/… there is an explicit **Behavior** type (“Other malware types: Microsoft also detects *Behavior* and *Tool* types”). Behavior-monitor Learn page: “Behavior monitoring detections use the Behavior malware naming type.” — [How Microsoft names malware](https://learn.microsoft.com/en-us/defender-xdr/malware-naming); [Behavior monitoring](https://learn.microsoft.com/en-us/defender-endpoint/behavior-monitor) (Microsoft Learn)
- **Event 1015** symbolic name `MALWAREPROTECTION_BEHAVIOR_DETECTED`. Message: “The antimalware platform detected suspicious behavior.” Fields: Name (threat name), ID, Severity, Category, Path, Detection Origin, Detection Type, Detection Source, Status, User, **Process Name**, Signature ID/Version, Engine Version, Target File Name. — [Microsoft Defender Antivirus event IDs](https://learn.microsoft.com/en-us/defender-endpoint/troubleshoot-microsoft-defender-antivirus) (Microsoft Learn)
- **Event 1116** `MALWAREPROTECTION_STATE_MALWARE_DETECTED`: “detected malware or other potentially unwanted software.” **Event 1117** `MALWAREPROTECTION_STATE_MALWARE_ACTION_TAKEN`: action taken (Clean / Quarantine / Remove / Allow / Block / No action). Both include Detection Origin, Detection Type, Detection Source, User, **Process Name**. Detection Source enum includes: User, System, **Real-time**, IOAV, **NIS (Network inspection system)**, IEPROTECT, ELAM, Remote attestation, **AMSI**. Detection Origin includes **Incoming traffic** and **Outgoing traffic**. — [same event-ID article](https://learn.microsoft.com/en-us/defender-endpoint/troubleshoot-microsoft-defender-antivirus) (Microsoft Learn)
- 1006 is the older “engine found malware” event; 1116 is the later “state” detection event. They are **not** synonyms of 1015. — [Windows Defender Events (legacy table)](https://learn.microsoft.com/en-us/previous-versions/orphan-topics/ws.11/dn913615(v=ws.11)); [Q&A distinction of 1006 vs 1116](https://learn.microsoft.com/en-us/answers/questions/1134018/distinction-between-certain-windows-defender-event)
- Client engines that can feed those events **after** execution: behavior monitoring (process sequence), memory scanning (no cloud counterpart), **network engine**, AMSI (only if a supported host submits content). Cloud counterpart of behavior monitoring is “Behavior-based ML engine” on process-tree sequences. — [adv-tech-of-mdav](https://learn.microsoft.com/en-us/defender-endpoint/adv-tech-of-mdav) (Microsoft Learn)
- Microsoft 2022 Sliver blog (vendor blog, not Learn) shows MDE alerts for **injection-related API calls**, captioned as the CRT quartet, **not** as `Behavior:Win32/CommandAndControl`. — [Looking for the ‘Sliver’ lining](https://www.microsoft.com/en-us/security/blog/2022/08/24/looking-for-the-sliver-lining-hunting-for-emerging-command-and-control-frameworks/)

### Inferences
- If an operator sees `Behavior:Win32/CommandAndControl.*!ml` plus event **1015**, that is the documented behavioral-blocking path: process-tree + runtime sequence sent to cloud ML, possibly with the network engine / NIS contributing “outgoing traffic.” It is **not** documented as “WinINet in the IAT.”
- Event **1116** alone is ambiguous: same event is used for file detections, AMSI script detections, NIS, and real-time. Use the **Detection Source** and **Name** fields (and whether 1015 also fired) to tell layers apart.
- “Contacting C&C to download payloads” in the containment article is a **technique category**, not a packet signature. Combined with the network engine blurb, it is the closest Microsoft Learn text to a live-implant C2 block — still not an API name.

### Gaps
- Microsoft does not publish which specific APIs (`WinHttpSendRequest`, `InternetConnectW`, `connect`, `VirtualAlloc`) are features of `Behavior:Win32/CommandAndControl.*!ml`.
- No public mapping of ETW-Ti event IDs (ALLOCVM_LOCAL, PROTECTVM_LOCAL, …) onto MDAV threat names.
- Subfamily names after the `.*` (the actual `CommandAndControl.A!ml` vs `CommandAndControl.B!ml` strings) are not listed on Learn; WDSI threat encyclopedia would have to be scraped per-name and was not enumerated in this pass.

## Elastic doubling-down ETW call stacks: unbacked RWX, LoadLibraryExW from unbacked, direct syscall

### Takeaway
Elastic’s public rule names for this layer are **not** “LoadLibraryExW from unbacked” as a single title. The Fortbridge UI string **“Network Library Loaded from Unbacked Memory”** matches the public GitHub rule **“Network Module Loaded from Suspicious Unbacked Memory”** (id `aa265fbd-…`), which fires on a **library-load event** of `ws2_32.dll` / `wininet.dll` / `winhttp.dll` whose call stack contains `Unbacked` (typical frame `ntdll.dll|kernelbase.dll|Unbacked`). Direct syscall is a **separate** 8.11 API-event rule on `VirtualAlloc*` / `VirtualProtect*` / `MapViewOfFile*` / `WriteProcessMemory` with behavior `direct_syscall`. Unbacked RWX is an **enrichment flag** (`unbacked_rwx`, `process.thread.Ext.call_stack_contains_unbacked`) consumed by many rules, not one rule.

### Cited Findings
- Elastic 8.11 API events (from ETW-Ti) and their behavior tags: `unbacked_rwx` = “An entry in the call stack is non-image and writable”; `direct_syscall` = “A syscall instruction originated outside of the Native API layer”; `native_api` = call went to undocumented Native API rather than Win32; `sensitive_api` / `shellcode` = executable non-image memory calling a sensitive API; `allocate_shellcode` = non-image executable memory allocating more executable memory; `execute_fluctuation` / `write_fluctuation` = PAGE_EXECUTE / PAGE_WRITE flipping. — [Doubling Down](https://www.elastic.co/security-labs/doubling-down-etw-callstacks) (Elastic Security Labs)
- **Windows API Call via Direct Syscall** (public artifact name **Suspicious Windows API Call via Direct Syscall**): `api where … process.Ext.api.behaviors == "direct_syscall" and process.Ext.api.name : ("VirtualAlloc*", "VirtualProtect*", "MapViewOfFile*", "WriteProcessMemory")`. Logic comment: “call stack is not starting with NTDLL.” — [Doubling Down](https://www.elastic.co/security-labs/doubling-down-etw-callstacks); [defense_evasion_suspicious_windows_api_call_via_direct_syscall.toml](https://github.com/elastic/protections-artifacts/blob/main/behavior/rules/windows/defense_evasion_suspicious_windows_api_call_via_direct_syscall.toml)
- **VirtualProtect via Random Indirect Syscall** (artifact: **VirtualProtect via Indirect Random Syscall**): `VirtualProtect*` where the call stack does **not** contain `ntdll.dll!NtProtectVirtualMemory` / `ZwProtectVirtualMemory`. — [Doubling Down](https://www.elastic.co/security-labs/doubling-down-etw-callstacks)
- **Image Hollow from Unbacked Memory**: `hollow_image` + `VirtualProtect*` + `*.dll*` + size ≥ 10000 + `call_stack_summary : "*Unbacked*"`. — [Doubling Down](https://www.elastic.co/security-labs/doubling-down-etw-callstacks)
- Other 8.11 rules that are API-named: **AMSI or WLDP Bypass via Memory Patching** (`VirtualProtect*` with `*W*` or `WriteProcessMemory*` targeting `amsi.dll` / `mpoav.dll` / `wldp.dll`); **Evasion via Event Tracing for Windows Patching** (`WriteProcessMemory*` of `ntdll.dll!Etw*` / `ntdll.dll!NtTrace*`); **Windows System Module Remote Hooking** (cross-process `WriteProcessMemory` of `ntdll.dll` / `kernelbase.dll`). Full 8.11 list is in the same post. — [Doubling Down](https://www.elastic.co/security-labs/doubling-down-etw-callstacks)
- **Network Module Loaded from Suspicious Unbacked Memory** (id `aa265fbd-4c57-46ff-9e89-0635101cc50d`, min endpoint 8.8.0, action `kill_process`): sequence of process start then `[library where dll.name in~ ("ws2_32.dll", "wininet.dll", "winhttp.dll") and process.thread.Ext.call_stack_contains_unbacked == true and call_stack_summary in ("ntdll.dll|kernelbase.dll|Unbacked", "ntdll.dll|iphlpapi.dll|Unbacked", "ntdll.dll|winhttp.dll|Unbacked", "ntdll.dll|kernelbase.dll|wininet.dll|Unbacked", wow64 variants, …)]`. Description: “load of a Windows network module by a process where the creating thread's stack contains frames pointing **outside any known executable image**.” — [defense_evasion_network_module_loaded_from_suspicious_unbacked_memory.toml](https://github.com/elastic/protections-artifacts/blob/main/behavior/rules/windows/defense_evasion_network_module_loaded_from_suspicious_unbacked_memory.toml)
- Almond Offensive (Nov 2025) quotes that same rule as the one that catches “shellcode loading a network module,” and states Elastic rules look for **unbacked** frames on **specific libraries** (to keep FPs down), not on every `LoadLibrary`. — [Evading Elastic EDR's call stack signatures with call gadgets](https://offsec.almond.consulting/evading-elastic-callstack-signatures.html) (independent blog)
- **Network Connect API from Unbacked Memory** (id `720e0265-03bc-4cb7-9116-7fad5ea9cdfc`, min endpoint 8.14.0): `api where process.Ext.api.name == "connect"` (Winsock) and `call_stack_final_user_module.name == "Unbacked"` with summaries like `ntdll.dll|mswsock.dll|ws2_32.dll|Unbacked`. Mapped to ATT&CK T1055 **and** TA0011 Command and Control. Action: `kill_process`. — [command_and_control_network_connect_api_from_unbacked_memory.toml](https://github.com/elastic/protections-artifacts/blob/main/behavior/rules/windows/command_and_control_network_connect_api_from_unbacked_memory.toml)
- Related public rules: **Rundll32 or Regsvr32 Loaded a DLL from Unbacked Memory**; **Parallel NTDLL Loaded from Unbacked Memory** (`dll.Ext.load_index >= 2` + unbacked stack — “direct system calls to evade … hooking”); **Network Library Load via LdrLoadDLL**; **Microsoft Common Language Runtime Loaded from Suspicious Memory**. — [protections-artifacts behavior/rules/windows](https://github.com/elastic/protections-artifacts/tree/main/behavior/rules/windows); [Upping the Ante](https://www.elastic.co/security-labs/upping-the-ante-detecting-in-memory-threats-with-kernel-call-stacks)
- 8.8 also shipped **Potential Operation via Direct Syscall** / **Potential Process Creation via Direct Syscall** (pre-8.11 API-event generation). — [Upping the Ante, Resources](https://www.elastic.co/security-labs/upping-the-ante-detecting-in-memory-threats-with-kernel-call-stacks)

### Inferences
- For a **running HTTP Sliver PIC**, the documented Elastic tripwire is **not** “Sliver YARA” and **not** “CreateThread.” It is: Go `LazyDLL` → `LoadLibraryExW` (`LdrLoadDll`) of `winhttp`/`wininet`/`ws2_32` with an `Unbacked` frame, and/or later Winsock `connect` from `Unbacked`.
- `direct_syscall` is an **ETW-Ti API-event** detection on alloc/protect/map/write, independent of library-load rules. A PIC that uses normal `ntdll!NtProtectVirtualMemory` does **not** hit `direct_syscall`; it can still hit `unbacked_rwx` / `sensitive_api` if the **caller** is non-image.
- Elastic “Unbacked” ≈ call-stack return address not in a known **image** module ≈ Windows `MEMORY_BASIC_INFORMATION.Type != MEM_IMAGE` for that frame.

### Gaps
- Fortbridge’s alert title **“Network Library Loaded from Unbacked Memory”** is not an exact GitHub `name =` string. Closest public name is **“Network Module Loaded from Suspicious Unbacked Memory.”** Whether the product UI shortens the name is not documented by Elastic.
- No public Elastic rule is literally named “LoadLibraryExW from unbacked memory.” The library-load rules key on **which DLL was loaded** + **call-stack Unbacked**, not on the Win32 symbol `LoadLibraryExW` as `process.Ext.api.name`. (The connect rule **does** key on API name `connect`.)
- Elastic does not publish the exact kernel heuristic that labels a frame `Unbacked` vs `MEM_MAPPED` vs stomped `MEM_IMAGE`.

## Fortbridge: string-clean then Elastic still flags LoadLibraryExW from unbacked; disk LoadLibrary of a DLL succeeded — MEM_IMAGE vs MEM_PRIVATE

### Takeaway
The API difference is **who maps the implant bytes**. Donut/`VirtualAlloc` of a `.bin` produces **private committed pages** (`MEM_PRIVATE`, Elastic `Unbacked`) with RWX; Go `windows.NewLazyDLL` then calls `LoadLibraryExW` **from that region**, so the network DLL load has an Unbacked frame. `LoadLibrary`/`LoadLibraryEx` of a **PE on disk** goes through the image mapper (`NtMapViewOfSection` / `LdrLoadDll` with an image section) and yields `MEM_IMAGE` — Elastic no longer sees `Unbacked` as the caller. That is **not** “a different Win32 function that avoids LoadLibrary”; Fortbridge still used LoadLibrary, but of a **file-backed image**. Memory YARA / Defender string rules still applied to the DLL on disk until those strings were renamed.

### Cited Findings
- Fortbridge: “Sliver leverages Donut to generate shellcode as a `.bin` file, which it allocates in Read/Write/Execute memory for execution.” Default Donut AMSI bypass (value 3) was signatured; they set bypass to 1. “When sliver initializes an http beacon it loads the libraries using the Go type LazyDLL which calls the windows API `LoadLibraryExW` under the hood. This results in an Elastic behavioral detection of `Network Library Loaded from Unbacked Memory`.” Module stomping was rejected because of implant size (~30 MB). Pre-loading libraries failed because `NewLazyDLL()` still calls `LoadLibraryExW`. Hardware-breakpoint hook to `GetModuleHandle` “did not bypass the alert.” — [Reforging Sliver](https://fortbridge.co.uk/research/reforging-sliver-how-simple-code-edits-can-outmaneuver-edr/) (Fortbridge)
- Fortbridge workaround: “writing an implant dynamic library to disk was the simplest solution.” Final loader: “a simple program that just loads the implant dynamic library from the same folder, finds the entry point export and **runs it in a new thread**.” That produced a callback “on a system with an elastic agent running.” Disk write **did** trip Defender YARA until ASCII strings were removed (`DllRegisterServer`/`DllUnregisterServer`/`DllInstall`, `GetJitter`, `VoidFunc`, `GetKill`, `AddTunnel`, `GetIsIOC`, ` Go buildinf:`). A last YARA hit appeared **only while the implant was running** and was fixed by renaming `bishopfox`. — [Reforging Sliver](https://fortbridge.co.uk/research/reforging-sliver-how-simple-code-edits-can-outmaneuver-edr/)
- Win32: `MEM_IMAGE` = pages “mapped into the view of an **image section**”; `MEM_PRIVATE` = private pages; `VirtualAlloc`’s allocation range is what `MEMORY_BASIC_INFORMATION.AllocationBase` refers to. Image mapping is what `LoadLibrary`/`LoadLibraryEx` of a PE file does; `VirtualAlloc` never creates `MEM_IMAGE`. — [MEMORY_BASIC_INFORMATION](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-memory_basic_information); [VirtualAlloc](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-virtualalloc) (Microsoft Learn)
- Elastic rule text for the network-module load: stack frames “pointing **outside any known executable image**”; summaries explicitly contain the token `Unbacked` after `kernelbase.dll`. Action is process kill. — [Network Module Loaded from Suspicious Unbacked Memory](https://github.com/elastic/protections-artifacts/blob/main/behavior/rules/windows/defense_evasion_network_module_loaded_from_suspicious_unbacked_memory.toml)
- Independent Chinese-language reversing of the same unbacked logic: detection of thread start address with `State == MEM_COMMIT` and `Type != MEM_IMAGE` (i.e. not image-backed). — [浅析异常线程检测逻辑（unbacked）](https://cn-sec.com/archives/3491515.html) (aggregator; treat as secondary)

### Inferences
- **Same Win32 name, different memory type.** `LoadLibraryExW` of `winhttp.dll` is benign when the **caller** is `MEM_IMAGE` (a real DLL/EXE). It is the documented Elastic signal when the **caller** is unbacked `MEM_PRIVATE` executable memory. Fortbridge did not find a different API; they changed the **allocation primitive** of the implant from `VirtualAlloc` (Donut) to the Windows image loader.
- `CreateThread` on the export of a disk DLL is a **new** thread whose start address is inside `MEM_IMAGE`. That is the opposite of “thread start in unbacked memory.”
- Defender’s remaining hits after the Elastic unbacked rule was avoided were **memory/file YARA on strings**, which is the third sensor class (not ETW, not IAT).

### Gaps
- Fortbridge does not print `VirtualQuery` output, so `MEM_IMAGE` vs `MEM_PRIVATE` is the Win32 explanation that matches Elastic’s “outside any known executable image,” not a field they logged.
- They did not publish whether a **memory-module** (manual map / reflective load, still `MEM_PRIVATE` or `MEM_MAPPED` but not a file-backed image) would still trip the same Elastic rule — only that disk `LoadLibrary` of a PE worked.
- Go `LazyDLL` always calling `LoadLibraryExW` even if the DLL is already loaded is a Go `x/sys/windows` behavior; this pass did not re-read the Go source to confirm current golang.org/x/sys.

## Does skipping CreateThread (direct CALL of PIC) still trip ALLOCVM / PROTECTVM?

### Takeaway
**Yes.** ETW-Ti ALLOCVM / PROTECTVM are logged from the **memory manager** (`MiAllocateVirtualMemory` / `NtProtectVirtualMemory`) when executable pages are created or protections change. They do not require `CreateThread` / `CreateRemoteThread` / `NtCreateThreadEx`. A direct CALL/JMP into PIC still needs those pages to be executable, so ALLOCVM (if allocated RWX) and/or PROTECTVM (if RW→RX/RWX) still fire. `CreateThread` is a **separate**, later execution artifact; skipping it removes thread-start-in-unbacked detections, not alloc/protect telemetry. gatari.dev empirically: Defender still flagged `VirtualAlloc(RWX)` + copy + **function-pointer CALL** with no `CreateThread`.

### Cited Findings
- `EtwTiLogAllocExecVm` is called from `MiAllocateVirtualMemory` when executable virtual memory is allocated. `EtwTiLogProtectExecVm` is called from `NtProtectVirtualMemory` when protection of executable VM is modified. These are kernel functions, not user-mode `CreateThread` hooks. — [Evading ETW-Based Detections](https://edivandh.github.io/evading-etw-based-detections/) (independent); [Detecting Process Injection with ETW](https://blog.redbluepurpl.com/windows-security-research/kernel-tracing-injection-detection) (independent, 2022)
- Elastic’s 8.11 API list for ETW-Ti **does not include `CreateThread`**. It includes `VirtualAlloc`/`VirtualProtect`/`MapViewOfFile` and the `Ex` / `MapViewOfFile2` variants, plus `QueueUserAPC`, `SetThreadContext`, `WriteProcessMemory`. Behaviors `unbacked_rwx`, `allocate_shellcode`, `execute_shellcode`, `execute_fluctuation` are defined on **memory protection / non-image executable regions**, not on thread creation. — [Doubling Down](https://www.elastic.co/security-labs/doubling-down-etw-callstacks)
- `PAGE_EXECUTE_READWRITE` (`0x40`) and `PAGE_EXECUTE_READ` (`0x20`) are the documented executable protections. `VirtualProtect` exists specifically to change a committed page’s protection (the RW→RX pattern). — [Memory Protection Constants](https://learn.microsoft.com/en-us/windows/win32/memory/memory-protection-constants); [VirtualAlloc](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-virtualalloc) (Microsoft Learn)
- gatari.dev 2024: after static hits were removed, Defender still caught: (1) Process Start, (2) `VirtualAlloc(PAGE_EXECUTE_READWRITE)`, (3) `RtlMoveMemory`, (4) **execution of code in the RWX section** via casting the pointer and calling it. Author’s words: that series “is *very* well known and even Windows Defender is able to pick up on common malicious patterns.” They then switched execution to `QueueUserAPC` (an API Elastic **does** list on ETW-Ti). — [A Trip Down Memory Lane](https://gatari.dev/posts/memory-lane/)
- Elastic `direct_syscall` rule keys on `VirtualAlloc*` / `VirtualProtect*` / `MapViewOfFile*` / `WriteProcessMemory` — again, **no CreateThread**. — [Doubling Down](https://www.elastic.co/security-labs/doubling-down-etw-callstacks)

### Inferences
- Direct CALL of PIC is an **IAT/execution-style** evasion (no `CreateThread` in the IAT, no new thread start address for `NtQueryInformationThread`). It is **not** an ETW-Ti ALLOCVM/PROTECTVM evasion.
- Allocating RWX in one `VirtualAlloc` produces **ALLOCVM** with executable protection (the “bad” one-shot). Allocating RW then `VirtualProtect` RX produces **PROTECTVM** (the RW→RX pattern Elastic tags as `execute_fluctuation` / `sensitive_api` depending on caller). Either path is visible without a thread API.
- Microsoft Learn never says “we only scan if CreateThread was used.” Memory scanning is a separate client engine that walks process VA.

### Gaps
- Microsoft does not publish whether MDAV’s behavior engine **requires** a thread-create event as a correlator for ALLOCVM, or whether ALLOCVM alone is enough for a `Behavior:*` name. gatari.dev is one independent data point that RWX+CALL without CreateThread was enough **in 2024** against Defender, not a vendor spec.
- Whether a true “execute without ever setting execute permission” trick (e.g. hijacking an existing RX image section / Mockingjay) avoids ALLOCVM/PROTECTVM is a **different** primitive; this question was only about skipping CreateThread on ordinary PIC.

## Beacon vs interactive session: same process? Microsoft 2022 CRT inject vs stock `interactive`

### Takeaway
Stock Sliver **beacon and session share one OS process**. Official tutorial: `interactive` “will spawn a **goroutine** running [the] session connection loop **in the same beacon process**.” They differ in **network cadence** (sleep vs long-poll / persistent socket), not in PID or in the Go/protobuf image. Microsoft 2022’s documented API sequence (`VirtualAllocEx` → `WriteProcessMemory` → `VirtualProtectEx` → `CreateRemoteThread`) is the **post-ex** path used by `migrate`, `sideload`, `spawndll`, `execute-assembly`, `msf-inject`, `getsystem` — **not** the stock implant’s own entry. Elastic separately documented Sliver `execute-assembly` loading `clr.dll` from unbacked memory. A disk-run EXE session is `MEM_IMAGE`; the same implant as Donut PIC is `MEM_PRIVATE`.

### Cited Findings
- Sliver tutorial: “Session can be spun up in our beacon process using the `interactive` command. Under the hood this will spawn a goroutine running session connection loop **in the same beacon process**.” Sessions = long-polling / persistent connection; beacons = periodic callback + sleep. `socks5` is session-only. — [2 - Beacons vs Sessions](https://sliver.sh/tutorials/?name=2+-+Beacons+vs+Sessions) (Sliver official)
- Wiki: beacons may be tasked to open interactive sessions over any compiled C2 using `interactive`; session-mode implants **cannot** convert to beacon. `shell` and `portfwd` require interactive sessions. — [Getting Started (wiki snapshot)](https://github.com/BishopFox/sliver/wiki/Getting-Started/fd5584d646f2e382ed899728124873315b402a6a)
- Microsoft 2022: “Sliver utilizes process injection as a core part of many **default commands**,” listing **`migrate`**, **`spawndll`**, **`sideload`**, **`msf-inject`**, **`execute-assembly`**, **`getsystem`**, plus extensions/BOFs. “As of this writing, the built-in Sliver **migrate** command migrates to a remote process using a classic combination of **VirtualAllocEx, WriteProcessMemory, VirtualProtectEx, and finally CreateRemoteThread**. Other commands such as Sideload, SpawnDll, and Execute-Assembly also rely on this combination.” MDE alert example: “A process was injected with potentially malicious code.” — [Looking for the ‘Sliver’ lining](https://www.microsoft.com/en-us/security/blog/2022/08/24/looking-for-the-sliver-lining-hunting-for-emerging-command-and-control-frameworks/) (Microsoft Security Blog, dated 2022-08-24)
- Current Sliver `task_windows.go`: `sysAlloc` uses `windows.VirtualAlloc` with `PAGE_EXECUTE_READWRITE` unless `rwxPages` is false (then `PAGE_READWRITE`); remote inject uses `VirtualAllocEx` + `VirtualProtectEx(PAGE_EXECUTE_READ)` + `CreateRemoteThread`. `ExecuteAssembly` starts a sacrificial process then injects. — [implant/sliver/taskrunner/task_windows.go](https://github.com/BishopFox/sliver/blob/master/implant/sliver/taskrunner/task_windows.go)
- Sliver docs: `execute-assembly` starts a sacrificial process (`notepad.exe` default) hosting a reflective DLL that loads the CLR; `--in-process` is the alternative. `sideload` on Windows converts the DLL to shellcode via sRDI and injects into a sacrificial process. — [Third Party Tools](https://sliver.sh/docs/?name=Third%20Party%20Tools)
- Elastic 8.8 worked example: Sliver `execute-assembly` → `clr.dll` load with `call_stack_summary : "*mscoreei.dll|Unbacked*"`. Rule name **Microsoft Common Language Runtime Loaded from Suspicious Memory**. — [Upping the Ante](https://www.elastic.co/security-labs/upping-the-ante-detecting-in-memory-threats-with-kernel-call-stacks)
- Microsoft 2022 also notes Sliver must **decrypt config in memory** to check in, and they scanned memory for those values — i.e. a memory-scan layer on the **implant process itself**, independent of inject. They contrast Cobalt Strike `sleep_mask`; Fortbridge later states Sliver still has **no sleep mask**. — [Looking for the ‘Sliver’ lining](https://www.microsoft.com/en-us/security/blog/2022/08/24/looking-for-the-sliver-lining-hunting-for-emerging-command-and-control-frameworks/); [Reforging Sliver](https://fortbridge.co.uk/research/reforging-sliver-how-simple-code-edits-can-outmaneuver-edr/)

### Inferences
- `interactive` does **not** spawn a new Windows process and does **not** by itself run the CRT inject quartet. Detection delta vs beacon is mainly **network volume / long-lived socket** (Defender network engine / NIS / `Behavior:Win32/CommandAndControl`) plus whatever extra post-ex the operator then runs.
- Microsoft’s 2022 “classic combination” is what fires MDE **“process was injected”** when the operator uses stock post-ex. It is **not** the API sequence of a quiet HTTP beacon that only does Go HTTP + `LoadLibraryExW`.
- A **disk EXE** beacon/session: image-backed (`MEM_IMAGE`), so Elastic unbacked-library rules should **not** fire on its own `LoadLibraryExW` of winhttp (caller is the EXE). A **Donut/PIC** beacon: unbacked caller, those rules **do** fire — Fortbridge’s result. Same implant, different loader, different layer.

### Gaps
- Microsoft 2022 is dated (Sliver injection internals may have gained alternatives since “as of this writing”). Current `task_windows.go` still shows the CRT quartet as the default remote path, but this pass did not audit every inject backend (e.g. APC).
- No Microsoft document compares detection rates of beacon-sleep vs session-long-poll for the **same** binary.
- Whether MDE’s injection alert requires the **remote** (`*Ex`) APIs or also fires on local `VirtualAlloc`+`CreateThread` is not stated; the blog example is remote.

## AMSI: native Go EXE vs PowerShell / .NET execute-assembly

### Takeaway
A **native Go Sliver EXE/PIC does not hit AMSI** by itself. AMSI is an opt-in scan interface that **hosts** call (`AmsiScanBuffer`). Microsoft Learn’s supported hosts are PowerShell, JScript, VBScript, WSH, **.NET Framework 4.8+ (assemblies)**, WMI, and (with Microsoft 365 Apps) Office JS/VBA/XLM. Python/Perl are explicitly unsupported. `execute-assembly` **does** enter AMSI because it loads the CLR, which scans in-memory `Assembly.Load` payloads. Donut’s default AMSI bypass is about that CLR/script path and is itself heavily signatured (Fortbridge disabled it). Patching `amsi.dll` is a **different** detection (Elastic/Defender AMSI-patch rules) and is not required for a pure Go implant.

### Cited Findings
- Supported scripting languages for MDAV AMSI: PowerShell, Jscript, VBScript, WSH (`wscript`/`cscript`), **“.NET Framework 4.8 or newer (scanning of all assemblies)”**, WMI. Office JS/VBA/XLM if Microsoft 365 Apps. “AMSI doesn't currently support Python or Perl.” Fileless techniques listed include reflective DLL injection (handled by **memory scanning + behavioral monitoring**, not AMSI) and script-based techniques (AMSI). — [AMSI integration with Microsoft Defender Antivirus](https://learn.microsoft.com/en-us/defender-endpoint/amsi-on-mdav) (Microsoft Learn)
- AMSI-paired ML in the cloud is “a pair of models for each of the scripting engines covered, including PowerShell, JavaScript, VBScript, and Office VBA macros.” — [adv-tech-of-mdav](https://learn.microsoft.com/en-us/defender-endpoint/adv-tech-of-mdav) (Microsoft Learn)
- Event 1006/1015/1116 Detection Source includes **“Antimalware Scan Interface (AMSI). Primarily used to protect scripts (PowerShell, VBS), though it can be invoked by third parties as well.”** — [Defender event IDs](https://learn.microsoft.com/en-us/defender-endpoint/troubleshoot-microsoft-defender-antivirus) (Microsoft Learn)
- .NET 4.8 CLR comments (quoted in research literature): `AmsiScanBuffer` “should only run on **in-memory loads**, `Assembly.Load(byte[])` for example. Loads from disk are already instrumented by Defender.” — [IronNetInjector paper citing CLR source](https://scispace.com/pdf/ironnetinjector-weaponizing-net-dynamic-language-runtime-2f1iirjx.pdf) (secondary; the CLR comment is the primary technical claim)
- Fortbridge: Sliver Donut generation “By default, Sliver enables Donuts AMSI bypass, which has heavy signature detection.” They changed bypass from 3 to 1 **because of signatures**, not because a native Go HTTP beacon needs AMSI. — [Reforging Sliver](https://fortbridge.co.uk/research/reforging-sliver-how-simple-code-edits-can-outmaneuver-edr/)
- Elastic 8.11 **AMSI or WLDP Bypass via Memory Patching** keys on `VirtualProtect*`/`WriteProcessMemory*` targeting `amsi.dll` / `mpoav.dll` / `wldp.dll` — i.e. the **patch**, not native Go. — [Doubling Down](https://www.elastic.co/security-labs/doubling-down-etw-callstacks)
- Sliver `execute-assembly` loads CLR in a sacrificial (or `--in-process`) process; Elastic used that as the unbacked-`clr.dll` example. — [Third Party Tools](https://sliver.sh/docs/?name=Third%20Party%20Tools); [Upping the Ante](https://www.elastic.co/security-labs/upping-the-ante-detecting-in-memory-threats-with-kernel-call-stacks)

### Inferences
- Native Go implant: detection layers are IAT/ETW/memory YARA/behavior/network — **not AMSI**.
- Operator runs `execute-assembly` or a PowerShell BOF/alias: **AMSI + CLR ETW + Elastic clr.dll-from-unbacked** all become in scope, in addition to the CRT inject APIs if a sacrificial process is used.
- Donut AMSI bypass is a **loader** concern when the shellcode hosts CLR/VBS, and it is a **signature** problem (IAT/strings of the bypass stub), which is why Fortbridge turned it off.

### Gaps
- Microsoft Learn does not mention Go. Absence from the supported-host list is the evidence; there is no sentence “Go binaries are not AMSI-scanned.”
- Whether some third-party AMSI provider scans **all** `NtMapViewOfSection` of executable images (beyond Microsoft’s documented hosts) is vendor-specific and not documented for MDAV.

## HTTP C2 default fingerprint (`.woff` / `.php` / `.js`) as network detector vs API detector

### Takeaway
Default Sliver HTTP procedural C2 (`.woff` stager, `.html` key exchange, `.php` session, `.js` poll, `.png` close; Apache/PHP fake headers) is a **network / URI / header** detector (Snort, Zeek, Packetbeat, Shodan JARM, NIS). It is **not** an API detector. The APIs that implement it (`LoadLibraryExW` of winhttp/wininet/ws2_32, `WinHttp*` / `Internet*`, Winsock `connect`) are generic; Elastic/Defender API-layer rules fire on **call-stack provenance** (unbacked) or **behavior ML / network engine**, not on the string `.woff`. Changing `http-c2.json` defeats the URI fingerprint and does **not** defeat `LoadLibraryExW` from unbacked memory.

### Cited Findings
- Default implant-side extensions (Sliver docs): `.woff` = stagers, `.js` = long poll, `.html` = key exchange, `.php` = session messages, `.png` = close. Everything in the path except the extension is ignored by the server. Config keys: `stager_file_ext`, `poll_file_ext`, `session_file_ext`, … — [HTTPS C2](https://sliver.sh/docs/?name=HTTPS+C2) (Sliver official)
- 2021 independent fingerprint: server pretends to be Apache+PHP (`Server: Apache/2.4.x (Unix)`, `X-Powered-By: PHP/7.x.x`, `Cache-Control: no-store, no-cache, must-revalidate`); router maps `*.txt` rsa, `*.jsp` start, `*.php` session, `*.js` poll, `*.png` stop, `*.woff` stager. Shodan query on that header set. — [Hunting Sliver (pat_h/to/file)](https://blog.tofile.dev/2021/09/04/sliver.html) (independent, dated 2021; defaults have been configurable since)
- Immersive Labs: same extension map; “Sliver’s HTTP settings are **highly configurable**, and the details below apply to the **default** configuration.” They published **Snort** rules and a **Sigma** rule for Zeek/PacketBeat — network/log detectors. Separate **memory** YARA on `sliverpb`. — [Detecting and decrypting Sliver C2](https://www.immersivelabs.com/resources/c7-blog/detecting-and-decrypting-sliver-c2-a-threat-hunters-guide); [SliverC2-Forensics](https://github.com/Immersive-Labs-Sec/SliverC2-Forensics)
- NetWitness: application rules on `(directory contains '.woff' || filename contains '.woff') && file.type='windows executable'` for the stager, and on default poll filenames (`bootstrap.js`, `jquery.min.js`, …) plus Chrome-like User-Agent — again network metadata. — [Sliver C2 – Network and Endpoint Detection with NetWitness](https://community.netwitness.com/s/article/689643)
- Microsoft 2022: infrastructure hunting via “unique HTTP header combinations and **JARM hashes**”; cites RiskIQ methodology. That section is **listener/server** fingerprinting, not a Windows API. — [Looking for the ‘Sliver’ lining](https://www.microsoft.com/en-us/security/blog/2022/08/24/looking-for-the-sliver-lining-hunting-for-emerging-command-and-control-frameworks/)
- Defender event 1116 Detection Source **NIS** = “Network inspection system”; Detection Origin can be Incoming/Outgoing traffic. Separate from AMSI/Real-time. — [Defender event IDs](https://learn.microsoft.com/en-us/defender-endpoint/troubleshoot-microsoft-defender-antivirus)
- Elastic **Network Connect API from Unbacked Memory** matches Winsock `connect` from `Unbacked` and is tagged Command and Control — an **API + call-stack** detector that does not inspect `.php`. — [command_and_control_network_connect_api_from_unbacked_memory.toml](https://github.com/elastic/protections-artifacts/blob/main/behavior/rules/windows/command_and_control_network_connect_api_from_unbacked_memory.toml)

### Inferences
- Treat HTTP default fingerprints and API/call-stack rules as **orthogonal**. OPSEC on `http-c2.json` addresses Zeek/Snort/Shodan. It does not address Fortbridge’s Elastic `LoadLibraryExW` from unbacked, nor ETW-Ti ALLOCVM, nor memory YARA on protobuf.
- A disk-backed HTTPS implant with a fully customized C2 profile can still be a `Behavior:Win32/CommandAndControl.*!ml` candidate **if** MDAV’s network/behavior ML scores the process tree + traffic, but that scoring is unpublished. The **documented** API-layer C2 detections in public Elastic rules are unbacked `LoadLibrary` of network DLLs and unbacked `connect`.

### Gaps
- No public Microsoft Learn article says MDAV NIS signatures include Sliver `.woff`/`.php`/`.js`. NIS is only named as a Detection Source enum.
- Default extension names have been user-configurable for years; any **current** network rule that still keys on `.woff` is hunting **defaults**, not all Sliver HTTP.

## Source-class legend used above

- **Microsoft Learn** — product documentation (engines, event IDs, Win32 APIs, AMSI host list, MITRE-style `Behavior:Win32/*` names).
- **Microsoft Security Blog 2022** — hunting writeup, not a contract. API sequence for stock post-ex; MDE alert text; memory config extraction; JARM/headers.

- **Independent** (gatari.dev, Immersive, pat_h/to/file, ETW-Ti reverse-engineering blogs) — useful for ALLOCVM/PROTECTVM internals and HTTP fingerprints; not Microsoft/Elastic docs.
