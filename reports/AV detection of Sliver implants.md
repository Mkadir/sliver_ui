# Scanners follow the unpacked implant

Antivirus and EDR products do not detect a Sliver C2 client as one hash or one “bad API.” They stack **six independent layers**: on-disk family YARA, generic Go PE-ML, post-decrypt **memory YARA**, kernel **ETW-Ti** on executable allocations, behavioral C2/injection ML, and **network fingerprints** of default HTTP/TLS. Generate format (`exe`, `shared`, Donut `shellcode`) changes only the **wrapper** scanners see at rest and the **memory type** of the first mapping: an OS-loaded EXE or DLL is file-backed **`MEM_IMAGE`**; Donut PIC from `VirtualAlloc` is unbacked **`MEM_PRIVATE`** until Donut’s own mapper runs, and that mapper still lands a pagefile-backed view unless a decoy `SEC_IMAGE` path is used ([Payload Compatibility](https://sliver.sh/docs?name=Payload+Compatibility); [TheWover/donut](https://github.com/TheWover/donut); [MEMORY_BASIC_INFORMATION](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-memory_basic_information)). After unpack, EXE, SHARED, and shellcode run the **same ~16–30 MB Go image**, so **`sliverpb` and protobuf RPC names remain if the teamserver is stock** — garble does not rename them ([Immersive Labs](https://www.immersivelabs.com/resources/c7-blog/detecting-and-decrypting-sliver-c2-a-threat-hunters-guide); [BishopFox/sliver#1760](https://github.com/BishopFox/sliver/issues/1760)). Unique SHA-256 and wrap XOR defeat exact-hash IOCs and some at-rest blob strings; they do **not** rewrite those names in process memory, and Microsoft’s memory-scanning engine has **no cloud counterpart** ([Advanced technologies of MDAV](https://learn.microsoft.com/en-us/defender-endpoint/adv-tech-of-mdav)). The documented Windows **triggers** are call-stack provenance and remote-inject sequences — `LoadLibraryExW` of `winhttp`/`wininet`/`ws2_32` from an **Unbacked** frame, Winsock `connect` from Unbacked, and `VirtualAllocEx` → `WriteProcessMemory` → `VirtualProtectEx` → `CreateRemoteThread` on post-ex — not the mere presence of `VirtualAlloc` or `LoadLibraryExW` in a Go IAT ([Fortbridge: Reforging Sliver](https://fortbridge.co.uk/research/reforging-sliver-how-simple-code-edits-can-outmaneuver-edr/); [Network Module Loaded from Suspicious Unbacked Memory](https://github.com/elastic/protections-artifacts/blob/main/behavior/rules/windows/defense_evasion_network_module_loaded_from_suspicious_unbacked_memory.toml); [Looking for the ‘Sliver’ lining](https://www.microsoft.com/en-us/security/blog/2022/08/24/looking-for-the-sliver-lining-hunting-for-emerging-command-and-control-frameworks/)). BishopFox treats AV evasion as **out of scope** ([Anti-virus Evasion](https://github.com/BishopFox/sliver/blob/master/docs/sliver-docs/pages/docs/md/Anti-virus%20Evasion.md)).

## Stock EXE, SHARED, and Donut fail different static scanners

On disk, format is a **wrapper class**, not a different implant. Microsoft lists default payloads as shellcode, executable, shared library/DLL, and service; operators who skip the default PE embed shellcode in a custom loader because **file-based** detection is the first surface, not because the inner image changes ([Looking for the ‘Sliver’ lining](https://www.microsoft.com/en-us/security/blog/2022/08/24/looking-for-the-sliver-lining-hunting-for-emerging-command-and-control-frameworks/)). A stock `exe` is a large unsigned Go PE (Immersive’s average **~16 MB**, Fortbridge **up to 30 MB**) with a real IAT, `gopclntab`, and plaintext protobuf. `shared` is the same c-shared Go image plus an **export directory**: CLI defaults `StartW,VoidFunc,DllInstall,DllRegisterServer,DllUnregisterServer` (`StartW` for rundll32, `VoidFunc` for PowerSploit `Invoke-ReflectivePEInjection`, COM names for `regsvr32`) ([BishopFox/sliver#1782](https://github.com/BishopFox/sliver/issues/1782); [v1.2.1 sliver.go](https://github.com/bishopfox/sliver/blob/v1.2.1/sliver/sliver.go)). Windows `generate --format shellcode` compiles a **PIE EXE** and converts it with Donut; BallisKit’s 2025 note is the accurate one: that “raw shellcode is a **wrapper over a PE anyway**” ([binaries.go](https://github.com/BishopFox/sliver/blob/master/server/generate/binaries.go); [BallisKit](https://blog.balliskit.com/tutorial-sliver-c2-with-balliskit-macropack-and-shellcodepack-452e94c24b19)).

Public **file YARA** is a consensus on implant ASCII, not on PE magic alone. Elastic `Multi_Trojan_Sliver` is three rules, all `scan_context = "file, memory"`: protobuf getters (`).RequestResend`, `).GetPrivInfo`), the Go package path `B/Z-github.com/bishopfox/sliver/protobuf/sliverpbb` plus RPC types (`InvokeSpawnDllReq`, `NetstatReq`, `HTTPSessionInit`, `ScreenshotReq`, `RegistryReadReq`), and a third rule that is **session-start/register bytecode** rather than strings ([Multi_Trojan_Sliver.yar](https://raw.githubusercontent.com/elastic/protections-artifacts/main/yara/rules/Multi_Trojan_Sliver.yar)). Immersive’s file rule requires PE/ELF/Mach-O magic **and** `sliverpb` **and** `github.com/bishopfox/` **and** `chacha20poly1305`; NCSC’s SVR advisory keys `/sliver/`, `sliverpb.`, and eight `*Req` names; ditekSHen/Malpedia and Wazuh reuse the same family; Chronicle GCTI matches C2 URL-scheme CMP immediates rather than protobuf names ([sliver.yar](https://raw.githubusercontent.com/Immersive-Labs-Sec/SliverC2-Forensics/main/Rules/sliver.yar); [NCSC gist](https://gist.github.com/ecapuano/2c59ff1ea354f1aae905d6e12dc8e25b); [Wazuh](https://wazuh.com/blog/detecting-sliver-c2-framework-with-wazuh/); [ditekSHen INDICATOR_TOOL_Sliver](https://github.com/ditekshen/detection/blob/e76c93dcdedff04076380ffc60ea54e45b313635/yara/indicator_tools.yar); [GCTI Sliver_Implant_64bit](https://github.com/chronicle/GCTI/blob/main/YARA/Sliver/Sliver__Implant_64bit.yara)). Elastic’s published Sliver YARA does **not** list `StartW`, `VoidFunc`, or ` Go buildinf:`. Those are the Fortbridge extract from [roadwy/DefenderYara](https://github.com/roadwy/DefenderYara): nine ASCII needles `DllUnregisterServer`, `DllRegisterServer`, `DllInstall`, `GetJitter`, `VoidFunc`, `GetKill`, `AddTunnel`, `GetIsIOC`, and ` Go buildinf:` (leading space). Fortbridge **removed unused exports** and **renamed `StartW`** separately; `StartW` was not in that nine-string list. Splunk ESCU “Suspicious Rundll32 StartW” is a **process-creation** hunt written for Cobalt Strike that also matches Sliver `rundll32 implant.dll,StartW` ([Reforging Sliver](https://fortbridge.co.uk/research/reforging-sliver-how-simple-code-edits-can-outmaneuver-edr/); [Splunk ESCU](https://research.splunk.com/endpoint/9319dda5-73f2-4d43-a85a-67ce961bddb7/)). Microsoft inbox names `Trojan:Win64/Sliver.D`, `ALF:Trojan:Win32/Sliver.A`, `VirTool:Win64/Splinter.A`, and `Behavior:Win32/Splinter.A` exist as family labels; Microsoft does **not** publish the bytes behind them ([WDSI Trojan:Win64/Sliver.D](https://www.microsoft.com/en-us/wdsi/threats/malware-encyclopedia-description?Name=Trojan:Win64/Sliver.D)).

Donut `.bin` trades one static class for another. Default Donut **Bypass=3 (continue on fail)** compiles an AMSI/WLDP/ETW patch into the **loader stub**, outside the optionally encrypted module. Operators attached MDAV **`Win32/AMSI_Patch_T.B13`** to stock Sliver generate-shellcode and **`Behavior:Win32/AMSI_PATCH_T.B12`** to `execute-shellcode` of Donut PIC — including a report that used **`-b 1` (none)** and still got B12 on C# Donut output ([sliver#1814](https://github.com/BishopFox/sliver/issues/1814); [sliver#2200](https://github.com/BishopFox/sliver/issues/2200); [donut#165](https://github.com/TheWover/donut/issues/165)). Entropy=3 can hide plaintext `sliverpb` in the file until decrypt; the AMSI stub remains. SGN, when applied, is a **self-modifying decoder that requires RWX** ([sliver#1410](https://github.com/BishopFox/sliver/issues/1410)). Stock EXE/SHARED do **not** contain that Donut stub.

A second static layer is **not Sliver-specific**. `Trojan:Win32/Wacatac.B!ml` is Microsoft PE-ML (`!ml` = classifier). Formidable tripped it on a **benign** unsigned Wails/Go GUI with **zero** sandbox dynamic detections; the author’s diagnosis is Go PE shape — large `.text`, **`gopclntab`**, `runtime.morestack_noctxt`, statically linked, no CRT — trained by Go-malware volume that includes Sliver ([Formidable](https://formidable.tools/posts/defender-wacatac-go-binary/)). Praetorian measured `-trimpath -ldflags "-s -w"` **increasing** detections, ML **over-indexing on `gopclntab`**, and a larger “ghost profile” dropping Microsoft Wacatac from **~95% to ~20%** on otherwise-identical payloads; cloud ML is more aggressive than local `MpCmdRun`, and models retrain on a roughly **daily** cadence ([Praetorian: Adversarial Oracles](https://www.praetorian.com/blog/llm-edr-signature-reduction/)). That classifier scores **EXE-shaped Go**. Raw `.bin` is not a PE; scanners that require MZ (Immersive file rule, PE-ML) miss it until a loader wraps it. SHARED is **not** quieter than EXE on disk: Fortbridge’s Defender hits on COM/`VoidFunc` export names are SHARED-specific, and disk `LoadLibrary` of an uncleaned DLL is still a **file scan** of those strings.

Garble (`ObfuscateSymbols`) does **not** rename protobuf-generated method and type names. Maintainers called this a **known issue**; custom AST work “some of it merged into v1.6” with **no ETA** for a comprehensive fix. #1760 closed in January 2026; Elastic’s public YARA still contained those strings in November 2026. Renaming protobuf is a **`.proto` + `make pb` + lockstep teamserver** change. A stock server still speaks `ScreenshotReq`; a stock client still embeds it ([BishopFox/sliver#1760](https://github.com/BishopFox/sliver/issues/1760); [The DFIR Report](https://thedfirreport.com/2024/08/12/threat-actors-toolkit-leveraging-sliver-poshc2-batch-scripts/)).

Linux public detection is thinner and mostly the **same family YARA** on ELF files and `/proc` maps. Do not extrapolate Windows `AMSI_PATCH` or unbacked-network-DLL rules to Linux.

## Unique hash and wrap XOR expire at callback

Microsoft’s hybrid stack scores a first-seen unsigned PE by **features, emulation, detonation, and behavior**; SHA-256 is a **cache key**, not a verdict. Cloud metadata includes PE attributes, ImpHash, signer info, MotW, download URL, **API calls**, and **process injection**. Block at First Sight locks an Internet-zone unknown for a default **10 seconds** (up to 60) while the cloud detonates; `.exe`/`.dll` are “safe samples” under default submission policy ([Cloud protection and sample submission](https://learn.microsoft.com/en-us/defender-endpoint/cloud-protection-microsoft-antivirus-sample-submission); [Block at first sight](https://learn.microsoft.com/en-us/defender-endpoint/configure-block-at-first-sight-microsoft-defender-antivirus)). SmartScreen file-hash reputation for an unsigned new hash starts at **zero**; “unknown” is not “trusted,” and EV certificates no longer confer instant reputation ([SmartScreen reputation](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation)). XOR of an embedded blob hides inner strings **at rest** until the emulator or the live process decrypts them; the emulator “scans behavior during emulation and **memory content at the end of emulation**” ([Advanced technologies of MDAV](https://learn.microsoft.com/en-us/defender-endpoint/adv-tech-of-mdav)). gatari’s 2024 lab is the empirical split: XOR beat **on-disk** signatures; `VirtualAlloc(PAGE_EXECUTE_READWRITE)` + copy + **direct CALL** of the RWX region was then killed **at runtime**, and a later VirusTotal upload turned the **entire file hash** known-bad — cloud analysis, not a new VDM offset ([A Trip Down Memory Lane](https://gatari.dev/posts/memory-lane/)).

Once the implant is executing, the object under scan is the **process address space**. Microsoft documents a dedicated **client** memory-scanning engine (“scans the memory space used by a running process to expose malicious behavior that could be hiding through code obfuscation”) with **N/A in cloud** ([Advanced technologies of MDAV](https://learn.microsoft.com/en-us/defender-endpoint/adv-tech-of-mdav)). Immersive’s one-line reason memory detection is easier: **the entire Go binary must be unpacked into memory regardless of packing or staged delivery**. Their **memory** rule is literally `sliverpb`, because the file rule’s magic/offsets fail on dumps ([Immersive Labs](https://www.immersivelabs.com/resources/c7-blog/detecting-and-decrypting-sliver-c2-a-threat-hunters-guide)). Elastic’s three Sliver rules are `file, memory`. Fortbridge still had a **runtime-only** YARA hit on `bishopfox` after disk strings were cleaned — format did not hide the string in RAM. Donut’s default header overwrite zeros or replaces DOS/PE headers; **code and data of the native PE remain** ([Donut README](https://github.com/TheWover/donut)). Sliver has **no sleep mask** in the public tree Fortbridge tested; idle beacons keep plaintext Go/protobuf resident ([Reforging Sliver](https://fortbridge.co.uk/research/reforging-sliver-how-simple-code-edits-can-outmaneuver-edr/)).

A first callback proves the **wrapper PE was allowed to run**, not that the implant is invisible. Unique wrap hash, XOR-at-rest, skip-`CreateThread`, hide-console, and short Sleep/RAM emulator gates are **pre-jump / hash-IOC** controls. They do not rewrite `ScreenshotReq` in the decrypted image. Client behavioral blocking then sends **process trees** to cloud ML and can kill a **running** artifact; MITRE-tactic names include `Behavior:Win32/CommandAndControl.*!ml`. Event **1015** is the dedicated “suspicious behavior” event; **1116/1117** are general malware detected / action-taken and also fire from file, AMSI, NIS, or real-time — they do not by themselves prove a behavioral detection ([Client behavioral blocking](https://learn.microsoft.com/en-us/defender-endpoint/client-behavioral-blocking); [Defender event IDs](https://learn.microsoft.com/en-us/defender-endpoint/troubleshoot-microsoft-defender-antivirus)). Inbox MDAV (`MsMpEng`) does this without an MDE license; MDE adds portal alerts and EDR-in-block-mode (off by default) ([Microsoft Defender Antivirus in Windows](https://learn.microsoft.com/en-us/defender-endpoint/microsoft-defender-antivirus-windows)).

`interactive` does not generate a new implant. Official tutorial: it spawns a **goroutine running the session connection loop in the same beacon process**. Beacon versus session is **network cadence** (sleep versus long-poll), not PID and not a second Go image ([Beacons vs Sessions](https://sliver.sh/tutorials/?name=2+-+Beacons+vs+Sessions)). Microsoft’s 2022 hunts extract **in-memory config** because the implant must decrypt it to check in — a memory-scan layer on the implant process itself, independent of later inject ([Looking for the ‘Sliver’ lining](https://www.microsoft.com/en-us/security/blog/2022/08/24/looking-for-the-sliver-lining-hunting-for-emerging-command-and-control-frameworks/)).

## Disk LoadLibrary maps MEM_IMAGE; VirtualAlloc PIC stays Unbacked

Microsoft’s 2017 reflective-DLL model did **not** signature Stephen Fewer’s loader blob. It scored **abnormal executable `VirtualAlloc`/`VirtualProtect`** in high-risk processes, including large RWX regions with PE-like content and **no backing module**. That class is still live as Elastic “Unbacked” call stacks and MDE injection alerts ([Detecting reflective DLL loading](https://www.microsoft.com/en-us/security/blog/2017/11/13/detecting-reflective-dll-loading-with-windows-defender-atp/); [Doubling Down](https://www.elastic.co/security-labs/doubling-down-etw-callstacks)). Sliver **implant** Windows shellcode is Donut, not sRDI (`sideload` docs still say sRDI; 2023 source tracing called `DonutShellcodeFromPE`). Generating `--format shared` and `LoadLibrary`’ing it from disk **does not** hit the 2017 model (Windows loader, `MEM_IMAGE`, module list populated). Generating `--format shellcode` and `VirtualAlloc`+CALL **does**.

Fortbridge’s 2025 sequence is the public A/B. Protobuf rename dropped Elastic **string** YARA; inlining `GetMaxConnectionErrors()` dropped bytecode rule `3d6b7cd3`; Donut Bypass **3→1** dropped the AMSI-stub class. Packers, self-inject, and hollowing of stock Sliver “proved ineffective” against Elastic and Defender. HTTP beacon init still used Go `windows.NewLazyDLL` → **`LoadLibraryExW`** of `ws2_32`/`wininet` from the PIC. Elastic alerted **“Network Library Loaded from Unbacked Memory.”** The public artifact title is **Network Module Loaded from Suspicious Unbacked Memory** (id `aa265fbd-…`): library load of `ws2_32.dll` / `wininet.dll` / `winhttp.dll` where `call_stack_contains_unbacked == true` and the summary is one of a short list ending in `Unbacked` (typical `ntdll.dll|kernelbase.dll|Unbacked`). Action is **`kill_process`**. A sibling rule, **Network Connect API from Unbacked Memory** (min endpoint 8.14.0), keys Winsock `connect` with `call_stack_final_user_module.name == "Unbacked"` and also `kill_process`. Module stomping failed because a **16–30 MB** Go implant has no realistic sacrificial `.text`; Donut decoy (`-j`) has the same size floor (`SEC_IMAGE` decoy must be ≥ `SizeOfImage`). Pre-loading DLLs failed because `NewLazyDLL()` still calls `LoadLibraryExW`. Hardware-breakpoint hooks did not clear the alert ([Reforging Sliver](https://fortbridge.co.uk/research/reforging-sliver-how-simple-code-edits-can-outmaneuver-edr/); [network-module toml](https://github.com/elastic/protections-artifacts/blob/main/behavior/rules/windows/defense_evasion_network_module_loaded_from_suspicious_unbacked_memory.toml); [connect toml](https://github.com/elastic/protections-artifacts/blob/main/behavior/rules/windows/command_and_control_network_connect_api_from_unbacked_memory.toml); [Almond](https://offsec.almond.consulting/evading-elastic-callstack-signatures.html)).

The workaround that produced a callback on a host with Elastic Agent was **not a different Win32 name**. It was **who maps the implant bytes**. Writing a **SHARED** implant to disk and `LoadLibrary`/`GetProcAddress`/`CreateThread` of the export goes through the image mapper (`NtMapViewOfSection` / `LdrLoadDll` with an **image section**) and yields **`MEM_IMAGE`**. Later `LoadLibraryExW` of `winhttp.dll` then has `sliver.dll` (image) on the stack, not `Unbacked`. `VirtualAlloc` never creates `MEM_IMAGE`. Donut without decoy uses `NtCreateSection(..., SEC_COMMIT, PAGE_EXECUTE_READWRITE)` — pagefile-backed, still unbacked to Elastic. Hasherezade’s contrast is the same Windows fact: manually mapped PEs land in **`MEM_PRIVATE`**; a legitimate loader mapping is **`MEM_IMAGE`** ([Donut inmem_pe.c](https://github.com/TheWover/donut/blob/master/loader/inmem_pe.c); [hasherezade](http://hasherezade.github.io/)). Disk SHARED still faced **static** Defender YARA until those nine ASCII strings and `bishopfox` were renamed. Fortbridge does **not** publish a live Microsoft cloud-ML “0 detections after rename” screenshot; Defender evidence in that paper is extracted YARA plus LitterBox. Aggregators that paraphrase “zero detections” add no independent lab.

An EXE started with `CreateProcess` is also `MEM_IMAGE`. Fortbridge chose a DLL because their packer story was “load a library from the same folder,” not because EXE is inherently hotter. There is **no** public 2022–2026 side-by-side MDAV/Elastic detection-rate table for otherwise-identical Sliver builds as EXE versus DLL versus Donut `.bin`. Rank **behavioral** noise from the cited writeups: Donut unbacked PIC (AMSI stub, RWX/SGN, unbacked network-module load) > remote CRT inject (`sideload`/`spawndll`/`migrate`) > disk EXE/DLL started by the OS. Rank **static** noise: disk EXE/DLL (SHARED with default COM/`VoidFunc` exports especially) > raw `.bin` (no MZ; Donut stub if Bypass≠1). After unpack, **memory YARA (`sliverpb`) does not rank formats**.

## Documented API triggers are provenance, not the IAT

Three sensor classes must stay distinct. **IAT** is names in the on-disk PE import directory — a file feature for PE-ML, not a runtime hunt. **ETW-Ti** (`Microsoft-Windows-Threat-Intelligence`) is kernel logging of `NtAllocateVirtualMemory` / `NtProtectVirtualMemory` / `NtMapViewOfSection` / `NtWriteVirtualMemory` from `ntoskrnl` (`EtwTiLogAllocExecVm`, `EtwTiLogProtectExecVm`); user-mode unhooking does not remove it; subscribers must be PPL-Antimalware. Elastic 8.11+ enriches those events with call-stack behaviors (`unbacked_rwx`, `direct_syscall`, `sensitive_api`, `allocate_shellcode`, `execute_fluctuation`) ([Doubling Down](https://www.elastic.co/security-labs/doubling-down-etw-callstacks)). **Memory scan** matches YARA in process VA after those APIs have already run, independent of how the bytes arrived.

Skipping `CreateThread` does **not** skip ALLOCVM/PROTECTVM. Those events fire when executable pages are created or protections change. A direct CALL/JMP into PIC still needs those pages executable. Elastic’s 8.11 ETW-Ti API list does **not** include `CreateThread`; it includes `VirtualAlloc`/`VirtualProtect`/`MapViewOfFile` and `Ex` variants, plus `QueueUserAPC`, `SetThreadContext`, `WriteProcessMemory`. gatari empirically: Defender still flagged `VirtualAlloc(RWX)` + `RtlMoveMemory` + **function-pointer CALL** with no `CreateThread` ([A Trip Down Memory Lane](https://gatari.dev/posts/memory-lane/)). Allocating RWX in one `VirtualAlloc` produces ALLOCVM with executable protection (`PAGE_EXECUTE_READWRITE` = `0x40`). Allocating RW then `VirtualProtect` RX produces PROTECTVM (Elastic `execute_fluctuation` / `sensitive_api` depending on caller). Either path is visible without a thread API ([Memory Protection Constants](https://learn.microsoft.com/en-us/windows/win32/memory/memory-protection-constants)).

A native Go EXE/PIC **does not hit AMSI**. AMSI is an opt-in host interface (`AmsiScanBuffer`). Microsoft’s supported hosts are PowerShell, JScript, VBScript, WSH, **.NET Framework 4.8+ (assemblies)**, WMI, and Office JS/VBA/XLM with Microsoft 365 Apps — not Go ([AMSI on MDAV](https://learn.microsoft.com/en-us/defender-endpoint/amsi-on-mdav)). `execute-assembly` **does** enter AMSI because it loads the CLR, which scans in-memory `Assembly.Load`. Elastic used Sliver `execute-assembly` as the 8.8 worked example of `clr.dll` loaded from unbacked RWX (`call_stack_summary : "*mscoreei.dll|Unbacked*"`) ([Upping the Ante](https://www.elastic.co/security-labs/upping-the-ante-detecting-in-memory-threats-with-kernel-call-stacks)). Patching `amsi.dll` is a **different** detection (Elastic **AMSI Bypass via Unbacked Memory** / **AMSI or WLDP Bypass via Memory Patching**; Defender `AMSI_Patch_T.*`) and is not required for a pure Go HTTP beacon.

Microsoft’s 2022 hunting piece treats **default post-ex commands** (`migrate`, `sideload`, `spawndll`, `execute-assembly`, `getsystem`, `psexec`, `shell`) as the high-signal surface, implemented with **`VirtualAllocEx` → `WriteProcessMemory` → `VirtualProtectEx` → `CreateRemoteThread`**. MDE example alert: **“A process was injected with potentially malicious code.”** GetSystem: `SeDebugPrivilege` then `CreateRemoteThread` into **`spoolsv.exe`**. Sideload/SpawnDll/Execute-Assembly: create and inject **`notepad.exe` within 10 seconds**. PsExec: `%WINDIR%\Temp\<10 alnum>.exe`, DisplayName **`Sliver`**, Description **`Sliver implant`**. Shell: exact command line `powershell.exe -NoExit -Command [Console]::OutputEncoding=[Text.UTF8Encoding]::UTF8` ([Looking for the ‘Sliver’ lining](https://www.microsoft.com/en-us/security/blog/2022/08/24/looking-for-the-sliver-lining-hunting-for-emerging-command-and-control-frameworks/); [SigmaHQ](https://github.com/SigmaHQ/sigma/blob/master/rules/windows/process_creation/proc_creation_win_hktl_sliver_c2_execution_pattern.yml); [VMware TAU](https://blogs.vmware.com/security/2023/01/detection-of-lateral-movement-with-the-sliver-c2-framework.html)). Hunt & Hackett add token APIs `OpenProcessToken` / `ImpersonateLoggedOnUser` / `DuplicateTokenEx` ([Hunting for a Sliver](https://www.huntandhackett.com/blog/hunting-for-a-sliver)). Current `task_windows.go` still uses `VirtualAlloc` RWX unless `rwxPages` is false, and remote inject still uses the CRT quartet ([task_windows.go](https://github.com/BishopFox/sliver/blob/master/implant/sliver/taskrunner/task_windows.go)). That sequence is **not** the idle HTTP poll loop of a disk-run EXE.

No public CrowdStrike Falcon or SentinelOne **implant family name** was published in the 2021–2026 open corpus searched for this report; absence of a public name is not evidence those products miss Sliver.

## Default HTTP and CRT post-ex stay independent of format

Default HTTP procedural C2 is a **network / URI / header** detector, not an API detector. Official mapping: **`.woff` stagers**, **`.js` long poll**, **`.html` key exchange**, **`.php` session**, **`.png` close**; everything in the path except the extension is ignored. Encoder is selected per message via a **nonce query parameter**; Base32/58/64 alphabets are modified; the English-words encoder uses 1,420 hardcoded words ([HTTPS C2](https://sliver.sh/docs/?name=HTTPS+C2); [Immersive Labs](https://www.immersivelabs.com/resources/c7-blog/detecting-and-decrypting-sliver-c2-a-threat-hunters-guide)). Immersive Snort still matches those extensions plus cookies `PHPSESSID|SID|SSID|APISID|csrf-state|AWSALBCORS` and path prefixes (`/php/`, `/api/`, `/js/`, `/static/`, …). Proofpoint ETPRO named `Sliver Framework HTTP C2 sessionInit` in October 2021. NetWitness 2025 still documents **`.woff` returning Windows executable magic** as the default stager. cyber.wtf Suricata 2024 hunts English-word encoder tokens in HTTP POST. Immersive states explicitly that **all of these paths and extensions are configurable**. Changing `http-c2.json` defeats the URI fingerprint and does **not** defeat `LoadLibraryExW` from unbacked memory, ETW-Ti ALLOCVM, or memory YARA on protobuf ([sliver.snort](https://github.com/Immersive-Labs-Sec/SliverC2-Forensics/blob/main/Rules/sliver.snort); [Proofpoint](https://www.proofpoint.com/us/blog/security-briefs/ta551-uses-sliver-red-team-tool-new-activity); [NetWitness](https://community.netwitness.com/s/article/689643); [cyber.wtf](https://cyber.wtf/2024/12/06/detection-of-c2-using-suricata/)).

TLS fingerprints are **server-side and version-split**. Published JARM hashes already disagree: pat_h/to/file 2021 mTLS `28d28d28d00028d00043d28d28d43d47390d982d099a542ccbc90628951062`; cedowens/Nuclei Go 1.15 `2ad2ad0002ad2ad00041d2ad2ad41da5207249a18099be84ef3c8811adc883`; Cybereason 2023 HTTPS `3fd21b20d00000021c43d21b21b43d41226dd5dfc615dd4a96265559485910` (and a second all-zero prefix hash), stated **not to work for mTLS**. Nuclei’s 2021-era hash is still in templates in 2026 and misses newer stacks. A widely cited **JA3 client** hash for the implant was not found. Hunters instead use **cert `CN=multiplayer` / issuer `O=operators`** (Shodan `product:sliver`, Red Canary 2025 BYOVM), TCP **31337** (multiplayer/gRPC), TCP **8888** (default mTLS), UDP **51820** (WireGuard). Cybereason: communications on **port 443 are too common to be a detection factor** ([Hunting Sliver](https://blog.tofile.dev/2021/09/04/sliver.html); [nuclei sliver-c2-jarm](https://github.com/projectdiscovery/nuclei-templates/blob/main/network/jarm/c2/sliver-c2-jarm.yaml); [LevelBlue/Cybereason](https://www.levelblue.com/blogs/spiderlabs-blog/sliver-c2-leveraged-by-many-threat-actors); [Beyond the bomb](https://www.zscaler.com/blogs/cybersecurity-best-practices/email-bombing-virtual-machine)). Palo Alto ATP June 2025 claims **Threat ID 89961** “Evasive Sliver C2 Traffic Detection” via a sequence neural net over TLS 1.3 records **without decrypt**. Vectra July 2026: encoder rotation produces multi-band sizes that break simple beacon clustering; their models still target Sliver-style timing/direction ([ATP June 2025](https://docs.paloaltonetworks.com/content/techdocs/en_US/advanced-threat-prevention/new-features/by-date/advanced-threat-prevention/june-2025.html); [Vectra](https://www.vectra.ai/blog/detecting-sliver-c2-when-advanced-beaconing-tries-to-hide-in-plain-sight)). Hunter’s Ledger 2026 skipped Suricata for one mTLS campaign because the channel was “indistinguishable from ordinary TLS without a captured JARM/JA3S” ([Hunter’s Ledger](https://the-hunters-ledger.com/hunting-detections/sliver-open-directory-detections/)).

Microsoft’s 2022 hunts **do not** key on the idle implant’s default HTTP/mTLS callback. They key on **post-ex API sequences and default configs**. Network-side default-HTTP catches are third-party IDS (ETPRO, Immersive Snort, Corelight, PAN ATP) plus MDAV’s unpublished network/behavior ML. Process names in the wild are Sliver’s generated two-word names (`WILD_PRIDE`, `nasty_roast`) or operator-chosen (`1HTTPS.EXE`), not a fixed `sliver.exe` ([The DFIR Report](https://thedfirreport.com/2024/08/12/threat-actors-toolkit-leveraging-sliver-poshc2-batch-scripts/)). Fortbridge’s remaining honesty after string-clean + disk `LoadLibrary`: **built-in commands still triggered Elastic behavioral alerts**. BallisKit wrapping a 1.7.3 implant with ShellcodePack reported stageless EXE command execution on tested (unnamed) EDRs and **EXE stagers caught when the second stage loaded in memory** — stage-2 is the unpacked implant again ([BallisKit](https://blog.balliskit.com/tutorial-sliver-c2-with-balliskit-macropack-and-shellcodepack-452e94c24b19)).

## Conclusion

Detection engineering on Sliver collapses to **which object each layer is allowed to see**. At rest the object is the wrapper: Go-PE ML and family YARA on EXE/DLL, Donut AMSI-stub YARA on `.bin`, export-table ASCII on SHARED. After first execution the object is the **plaintext Go implant in that PID**, and unique hash / XOR / skip-CreateThread / short Sleep have already been spent. The only format choice that changes a **documented 2024–2026 EDR rule** rather than a string is the mapping primitive — disk image-section `LoadLibrary` (`MEM_IMAGE`) versus `VirtualAlloc` PIC (`Unbacked`) — and even that leaves `sliverpb` in the view for the client memory scanner. Protobuf RPC identifiers are a **client/server contract**: they remain in the implant for as long as the teamserver is stock, which is why garble never closed Elastic `Multi_Trojan_Sliver` and why Fortbridge’s working path was a **forked schema**, not a smarter wrapper.
