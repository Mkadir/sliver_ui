# Ciphertext defeats hashes, not EDR

**Encrypt-at-rest for Sliver shellcode, shared libraries, and staged payloads is real, routinely used by authorized red teams and threat actors, and partially available inside Sliver—but it is not a general AV/EDR bypass.** Ciphertext on disk defeats exact hashes of a known implant blob and many plaintext string YARA rules; it does not defeat stub/loader signatures, entropy heuristics, sandbox detonation of the decrypt path, or behavioral EDR after decrypt (unbacked RX, RW→RX, reflective load, network beacon). BishopFox places AV evasion outside Sliver’s scope and points operators at packers, crypters, and stagers ([Sliver Docs: Anti-virus Evasion](https://sliver.sh/docs?name=Anti-virus+Evasion)). Native Sliver covers stage AES/RC4, Windows Donut `entropy=3`, and polymorphic shellcode encoders (SGN/XOR); true EXE/DLL encrypt-on-disk still requires an external loader. Sliver UI should add this as a **Loaders** concern—stage AES + custom stage-0 first, optional AES stub templates next, external checklists always—never as an Implants “FUD” checkbox. This report assumes **authorized red-team / lab / adversary-simulation** use only.

## Hash evasion is true; full AV bypass is not

The operator mental model—“if the beacon is encrypted on disk, AV that hashes the file will miss it, then we decrypt in memory and run”—is **half right**. Encrypting or encoding the implant changes its content hash, so static IOCs keyed on a known plaintext Sliver PE or shellcode sample miss the ciphertext blob. MITRE frames this as T1027 / T1027.013 (Obfuscated / Encrypted/Encoded File) and notes that reflective loading can keep payloads encrypted until execution ([MITRE T1027](https://attack.mitre.org/techniques/T1027/); [MITRE T1027.013](https://attack.mitre.org/techniques/T1027/013/); [MITRE T1620](https://attack.mitre.org/versions/v17/techniques/T1620)). Sandfly’s Linux analysis states the same split cleanly: encrypting the binary on disk evades legacy file YARA and traditional AV easily; the **running process** is the real detection target ([Sandfly: Detecting Bincrypter](https://sandflysecurity.com/blog/detecting-bincrypter-linux-malware-obfuscation)).

What the mental model misses is that modern AV/EDR does not “only hash the file.” Defenders also apply YARA and ML to the **stub**, high-entropy / packer heuristics (including `math.entropy` rules and packer-family markers), on-access scanning of whatever lands on disk, cloud sandbox detonation of the decrypt→allocate→execute path, AMSI inspection after de-obfuscation for scripted loaders, behavioral API and call-stack rules after plaintext appears in memory, and periodic memory scanners while the implant is awake ([MITRE DET0378](https://attack.mitre.org/detectionstrategies/DET0378); [Unprotect ScrubCrypt YARA](https://unprotect.it/detection-rule/yara_si_crypt_scrubcrypt_bat_jan24/); [Microsoft Learn: AMSI on MDAV](https://learn.microsoft.com/en-us/defender-endpoint/amsi-on-mdav); [Elastic: Doubling Down ETW Call Stacks](https://www.elastic.co/security-labs/threat-command/doubling-down-etw-callstacks)). NorthSec’s entropy talk documents that encrypting shellcode **raises** entropy and that some engines treat that as a suspicion signal ([NSEC talk: Evading AV/EDR Entropy Checks](https://www.youtube.com/watch?v=eXAYV7lKHHw)). Fortbridge’s April 2025 Elastic + Defender lab tested “encrypted implant in a loader” via self-injection or process hollowing and reported those paths **ineffective** without deeper implant customization; success came from string/protobuf/export renames plus a disk-backed DLL load, not from encrypt-at-rest alone ([Fortbridge: Reforging Sliver](https://fortbridge.co.uk/research/reforging-sliver-how-simple-code-edits-can-outmaneuver-edr)).

**Verdict:** treat encrypt-at-rest as **table stakes against static hash/string IOCs of the inner implant**, not as EDR evasion. Guaranteed “FUD” is not a credible product claim for any UI checkbox.

## Operators already ship decrypt-then-execute chains

OPSEC-conscious operators treat a vanilla Sliver EXE on disk as a lab artifact. Production initial access almost always routes through a crypter, packer, loader, or AES-staged shellcode so static signatures of the C2 PE miss. Microsoft observed actors generating Sliver shellcode and embedding it in custom loaders such as Bumblebee/COLDTRAIN, and warned that hunting must follow loader TTPs and in-memory config extraction rather than static PE hashes alone ([Microsoft: Looking for the Sliver lining](https://www.microsoft.com/en-us/security/blog/2022/08/24/looking-for-the-sliver-lining-hunting-for-emerging-command-and-control-frameworks/)). HarfangLab documented a 2024 “Supposed Grasshopper” chain where a Nim downloader fetched a ~15 MB Donut stage that patched AMSI/WLDP then mapped Sliver in memory ([HarfangLab: Supposed Grasshopper](https://harfanglab.io/insidethelab/supposed-grasshopper-operators-impersonate-israeli-gov-private-companies-deploy-open-source-malware/)). Hunter’s Ledger recovered a 2026 open-directory build workspace: PowerShell stager → ScareCrow-wrapped loader with encrypted chunks → Donut AES-128-CTR over Sliver PE → beacon in a hollowed process, with rebuild polymorphism making hash IOCs fragile within minutes ([Hunter’s Ledger: Sliver open directory](https://the-hunters-ledger.com/reports/sliver-open-directory/)).

The canonical authorized chain is generate implant (often PE or raw shellcode) → convert/pack (Donut, Amber, sRDI) → encrypt blob → deliver a stub that decrypts into allocated memory → protect RX → create thread / APC / export call. Variants embed ciphertext in the stub (ScareCrow AES/ELZMA/RC4), keep a split stub + encrypted `.bin`, or fetch encrypted stage-2 over HTTPS (Sliver stage-listener AES). BallisKit’s 2025 Sliver tutorial states it is generally good practice to load the C2-generated DLL or EXE with ShellcodePack rather than rely on the C2’s own loader ([BallisKit: Sliver + MacroPack/ShellcodePack](https://blog.balliskit.com/tutorial-sliver-c2-with-balliskit-macropack-and-shellcodepack-452e94c24b19)). Peer C2 UIs already treat this as packaging, not implant compile flags: Cobalt Strike patches XOR-obfuscated Beacon into Artifact Kit templates and warns that kits get signatured over time; Mythic uses wrapper payload types and Donut build knobs; Havoc documents Demon as not designed to be evasive and expects external loaders; Nighthawk markets NHLoader with stacked environmental and remote keying ([HelpSystems Artifact Kit](https://hstechdocs.helpsystems.com/manuals/cobaltstrike/current/userguide/content/topics/artifacts-antivirus_artifact-kit-main.htm); [Mythic Building Payloads](https://docs.mythic-c2.net/message-flow/building-payloads); [Havoc Agent](https://havocframework.com/docs/agent); [MDSec: Nighthawk 0.2](https://www.mdsec.co.uk/2022/05/nighthawk-0-2-catch-us-if-you-can/)). Environmental keying (hostname/domain-derived decrypt keys, MITRE T1480.001) appears in packers such as PEzor’s `-xorkey` and high-OPSEC packages, but is less universal than embedded AES keys ([MITRE T1480.001](https://center-for-threat-informed-defense.github.io/mappings-explorer/attack/attack-16.1/domain-enterprise/techniques/T1480.001/); [PEzor](https://github.com/phra/PEzor); [TrustedSec Execution Guardrails](https://trustedsec.com/blog/execution-guardrails-no-one-likes-unintentional-exposure)).

## Sliver encrypts stages and shellcode, not EXE downloads

`generate` does **not** encrypt EXE, service, or shared-library blobs at rest. It can garble symbols (`ObfuscateSymbols`), apply limited `Evasion`, and—for **shellcode format only**—optionally Donut-encrypt the embedded PE on Windows (`--shellcode-entropy 3` = random names + symmetric encryption) and/or post-process with polymorphic encoders (SGN / XOR / XOR_DYNAMIC) that prepend a self-decoder. Raw PE/DLL downloads remain plaintext binaries; encoder flags are ignored when format ≠ shellcode ([Sliver Stagers](https://sliver.sh/docs?name=Stagers); [Sliver Anti-virus Evasion](https://sliver.sh/docs?name=Anti-virus+Evasion)). Stage encryption is the main native “ciphertext until the stager decrypts” feature: after building stage-2, Sliver can compress then AES-CBC (PreludeEncrypt, IV prepended) or RC4; the stager must fetch, decrypt (drop leading IV for AES), decompress, then allocate and execute. In 1.7.3, client `stage-listener` effectively supports **TCP** staging; HTTP encrypted stages should use `profiles stage` / `GenerateStage` + HTTP C2 `stagerHandler` rather than assuming `stage-listener --url http://…` still works ([BishopFox/sliver#2009](https://github.com/BishopFox/sliver/issues/2009); [Sliver Stagers](https://sliver.sh/docs?name=Stagers)). A single Implants “encrypt payload” checkbox would be misleading: it would no-op on EXE/shared and conflate polymorphic self-decoders with keyed encrypt-at-rest.

| Capability | Native in Sliver 1.5–1.7? | Where / notes |
|---|---|---|
| Garble symbol obfuscation | Yes | `generate` / profiles (`ObfuscateSymbols`) — not ciphertext |
| Limited evasion hooks | Yes | `generate --evasion` |
| Encrypt EXE/DLL file on disk | **No** | External crypter/loader (ScareCrow, PEzor, Nimcrypt2, ShellcodePack, custom AES) |
| Donut module encryption (`entropy=3`) | Yes (Windows shellcode) | `ShellcodeConfig.Entropy`; key travels with Donut stub |
| Donut AMSI bypass mode | Yes (Windows shellcode) | `ShellcodeConfig.Bypass` (default continue); often signatured |
| SGN / XOR / XOR_DYNAMIC | Yes (shellcode blob) | Polymorphic **self-decoder**, not keyed encrypt-at-rest |
| Shellcode RDI (DLL → PIC) | Yes | `ShellcodeRDI` RPC |
| Stage AES-CBC / RC4 + compress | Yes | `stage-listener` (TCP in 1.7.3), `profiles stage` / `GenerateStage` |
| HTTP(S) stage-listener | Broken/removed on 1.7 master | Prefer TCP listener or `profiles stage` + HTTP C2 |
| Custom decrypting stager | External | Docs provide C# samples; stock MSF stagers are signatured |
| Packers / commercial crypters | External | PEzor, ScareCrow, Nimcrypt2, Amber, ShellcodePack, Artifact Kit |

After decrypt, Elastic-class agents enrich VirtualAlloc / VirtualProtect / MapViewOfFile with kernel ETW call stacks and label `unbacked_rwx`, `allocate_shellcode`, hollow/unbacked image patterns, and network libraries loaded from unbacked memory—the exact post-decrypt shape Fortbridge still tripped after static scrubbing ([Elastic: Doubling Down](https://www.elastic.co/security-labs/threat-command/doubling-down-etw-callstacks); [Elastic: Upping the Ante](https://www.elastic.co/security-labs/upping-the-ante-detecting-in-memory-threats-with-kernel-call-stacks); [Fortbridge](https://fortbridge.co.uk/research/reforging-sliver-how-simple-code-edits-can-outmaneuver-edr)). Memory scanners catch decrypted resident shellcode; sleep encryption (Ekko-class) narrows the idle YARA window but adds protect-flip / timer / APC telemetry and does nothing for initial delivery ([Binary Defense: Understanding Sleep Obfuscation](https://binarydefense.com/resources/blog/understanding-sleep-obfuscation); [Microsoft Sliver lining](https://www.microsoft.com/en-us/security/blog/2022/08/24/looking-for-the-sliver-lining-hunting-for-emerging-command-and-control-frameworks/)). Encrypted PE + stub, stage-0 fetch of ciphertext, and sleep encryption therefore defeat **different layers** and leave different residue: (a) fights inner-file IOCs but exposes stub and post-decrypt behavior; (b) shrinks first-drop footprint but adds network retrieval and the same in-memory controls; (c) only helps idle memory scans.

## Ship encrypt-at-rest under Loaders, not Implants

Sliver UI should add encrypt-at-rest capability, aligned with the existing Loaders plan language: network OPSEC stays on `/http-c2`; host/payload OPSEC belongs on **Implants + Loaders**; runtime hygiene stays in session Advanced tools and checklists. Peer pattern to copy is Havoc-level honesty (external loaders expected) plus Mythic-lite wrappers via templates—not a commercial NHLoader productization or a crypter GUI. Ranked product options: **A** native GenerateStage / stage-listener AES + custom stage-0 decrypt stubs (ship first); **B** post-process AES into downloadable lab stub templates (ship carefully); **D** document-only external appendix (always as copy layer); **C** shell out to Donut CLI from the UI host (**reject**—Sliver already embeds Donut for `format shellcode`, and host RCE surface is unjustified) ([Sliver Stagers](https://sliver.sh/docs/?name=Stagers); [LOADER_AV_OPSEC_PLAN.md](../docs/LOADER_AV_OPSEC_PLAN.md); [TheWover/donut](https://github.com/TheWover/donut)).

Phased recommendation for this fork:

| Phase | Deliverable | Honesty constraint |
|---|---|---|
| **P0–P1 (unchanged MVP)** | `/loaders`: Source → optional RDI → SGN/XOR encode → download; wire encoder APIs + `SGNEnabled`; Implants “Send to Loaders” | Copy already says prefer encrypted stage / external loader; do not email plaintext shellcode |
| **P1 / Phase 6 (Option A)** | Stage Listeners with AES/RC4/compress; show key/IV **once**, never store in UI DB; custom stage-0 templates (GET `*.woff`, decrypt matching Sliver IV framing, VirtualAlloc/exec); GenerateStage with MSF-signature warning; retire dead `POST /api/msf/stage` | AES-CBC-128 is **obfuscation-grade**; prefer custom stubs over stock MSF; version-gate TCP vs HTTP staging ([#2009](https://github.com/BishopFox/sliver/issues/2009)) |
| **P2 / Phase 4–7 (Option B)** | Export encrypted shellcode + C/C#/Go stub project (key patched or sidecar); hide-console default on; persistence / watchdog **off** by default | Lab examples only; stub itself will be YARA’d over time (same failure mode as stock Artifact Kit) |
| **Always (Option D)** | External appendix: Donut `-e 3`, ScareCrow/ShellcodePack/PEzor/Nimcrypt2, TrustedSec keying, environmental/DNS keying as operator exercise | Documents the real OPSEC stack BishopFox already points to |
| **Non-goals** | Commercial crypter, PE infection GUI, in-UI Donut CLI, silent AV-kill auto-heal, Implants “encrypt payload” FUD toggle | Outside Sliver RPC or dishonest UX |

Key handling must match Sliver CLI and the plan’s non-goals: generate or accept key/IV in the stage/stub form, display once for copy or stub embed, never persist in Sliver UI’s database. Environmental and DNS remote keying stay checklist + advanced template only—high OPSEC value, not a Sliver RPC ([TrustedSec Execution Guardrails](https://trustedsec.com/blog/execution-guardrails-no-one-likes-unintentional-exposure); [MDSec Nighthawk 0.2](https://www.mdsec.co.uk/2022/05/nighthawk-0-2-catch-us-if-you-can/)). Required banner language: encrypt-at-rest hides bytes from disk scanners and casual staging sniffing; it does not stop EDR behavioral detection; Sliver stage AES is obfuscation-grade; unique stubs beat shared UI templates over time; **no UI option can guarantee evasion**. Success metric remains fewer wrong packages (raw PE email, plaintext shellcode attachment), not a VirusTotal score.

## Conclusion

The useful product correction is narrower than “add a crypter”: Sliver already owns the pieces that make encrypt-at-rest honest for operators—stage AES/RC4, Donut entropy for Windows shellcode, and polymorphic encoders—while leaving EXE/DLL disk encryption to the external tooling ecosystem BishopFox endorses. Wiring those native paths under `/loaders` with show-once keys and custom decrypt stubs closes the Artifact-Kit gap without pretending ciphertext outruns Elastic call stacks or Defender cloud reputation. What changes for this UI is the default delivery story: generate beacon shared/shellcode against a customized HTTP profile, stage or wrap under Loaders so the implant is not plaintext on disk, execute via sideload or in-memory tools with a checklist gate, and treat ScareCrow-class custom loaders as the advanced external layer rather than a missing Implants checkbox.
